# Отчёт: one-car-order — заказ = одна машина

## Что сделано

У заказа теперь ровно одна машина: `tasks.car_id NOT NULL` со ссылкой на справочник `equipment`.
Миграция 0017 переносит машины из `task_equipment` в три шага:
1. Машина клиента заказа, чаще всего указанная в услугах, затем по госномеру.
2. Иначе первая машина клиента, действующая раньше удалённой.
3. Иначе новая машина с госномером из названия заказа.

Затем удаляются `task_equipment` и `subtasks.equipment_id`.

Заказ без машины создать нельзя. Машина и клиент задаются только при создании: `PUT /tasks/:id`
отклоняет `client_id`/`equipment_id` (400). Убраны эндпоинты `/tasks/:id/equipment`, блок
добавления/удаления машин в карточке и выбор машины в услугах. Комплектность и состояние
удалены полностью, это решение пользователя.

В карточке существующего заказа — строка «госномер · владелец · История работ», только для
чтения. Акты приёмки и выдачи показывают только госномер. История машины работает через
`car_id`. Справочник машин у клиента и раздел «Удалённые» не изменились.

## Known issues / as-is

- Инвариант «клиент заказа = владелец машины» держит сервис (машина неизменна после создания).
  Составной FK `(car_id, client_id)` не сделан осознанно.
- Комплектность и состояние из `task_equipment` миграцией не переносятся, down их не вернёт.
- В dev-БД 4 заказа с несколькими машинами перенесены по старому правилу (по госномеру). Их
  бэкфилл прошёл до правки шага 1.
- Возможный deadlock «создание заказа ↔ удаление клиента» был и до фичи (вне скоупа ревью).
- Отклонение от §TD-3: по просьбе пользователя дальнейшие e2e гоняются headless
  (`E2E_HEADLESS=1`). Прогоны этой фичи шли headed.
