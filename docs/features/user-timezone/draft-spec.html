После мержа этой части: у каждого пользователя есть часовой пояс (по умолчанию Алматы); все существующие экраны и печатные формы показывают дату и время по нему, а не по браузеру или серверу. Перемещения — ещё старый экран /stock-transfers, его время тоже идёт по поясу. Фильтра «период» в списке перемещений ещё нет (часть 4 transfers-partners).

§1. Суть задачи

Настройка часового пояса у пользователя и показ всех дат и времени системы по ней. Для всех ролей: склады и сотрудники в разных городах (Алматы, Москва).

Бизнес (что делает пользователь/процесс):

  1. 1Пользователь сам выбирает свой часовой пояс в сайдбаре, рядом с «Тема» и «Выйти» (§8.1) — DS-033.
  2. 2Администратор задаёт пояс любому сотруднику в «Администрирование → Сотрудники» (§8.1) — DS-056.
  3. 3На всех экранах и в печатных формах даты и время показаны в поясе смотрящего пользователя — DS-031, DS-032.

Логика (правила системы):

  1. 4Время: хранение — UTC (timestamptz), как сейчас; показ — по timezone пользователя (IANA), не по браузеру и не по поясу сервера — DS-031.
  2. 5Умолчание — Asia/Almaty (UTC+5) для новых и существующих пользователей — DS-033.
  3. 6Охват — все места, где показывается дата или время (перечень — §8.1 «Где применяется» и §Impact) — DS-032.
  4. 7«Сегодня / завтра / просрочен» для срока заказа на доске считается по текущей дате в поясе пользователя — DS-032.
  5. 8Исполнитель меняет только свой пояс; чужой — только администратор — DS-056.
  6. 9Конкурентный доступ: запись своего пояса → last-write-wins (одно поле, один владелец); правка сотрудника администратором → как сейчас у PUT /api/v1/users/:id (поведение не меняется), поле timezone при отсутствии в теле не трогается — поэтому правка сотрудника из устаревшей формы не затирает пояс, который сотрудник только что сменил сам — DS-033, DS-056.

Техника (API/данные/интеграции):

  1. 10users.timezone — новая колонка (§4.1), своя миграция.
  2. 11Новый PUT /api/v1/users/me/timezone; поле timezone в POST /api/v1/users, PUT /api/v1/users/:id, GET /api/v1/users, GET /api/v1/users/:id, GET /api/v1/auth/me (§6).
  3. 12SSR: пояс текущего пользователя доступен layout'у (атрибут data-timezone на <body>) и шаблонам (перевод time.Time в пояс перед форматированием).
  4. 13JS: единый форматтер даты/времени с timeZone вместо четырёх локальных копий.

UI (графическая часть):

  1. 14Select «Часовой пояс» в сайдбаре всех страниц (§8.1).
  2. 15Поле «Часовой пояс» в форме сотрудника (§8.1).
  3. 16Правка форматирования времени на существующих экранах: карточка заказа, доска, «Выплаты», «Перемещения» (старый экран), история оборудования, две печатные формы (§8.1 «Где применяется»).

Out-of-scope:

  1. 17Фильтр «период» в списке перемещений и границы дня по поясу — часть 4 transfers-partners (DS-034).
  2. 18Экран профиля пользователя — не заводится; достаточно select в сайдбаре (DS-033).
  3. 19Автоопределение пояса по браузеру — нет: умолчание фиксированное, Алматы (DS-033).
  4. 20Пояс склада или документа — нет: пояс принадлежит пользователю (DS-031).
  5. 21Поля-даты без времени (tasks.due_date) не сдвигаются: это календарная дата; по поясу считается только «сегодня» (DS-032).

§2. Интеграции и master-data

Не применимо: внешних систем нет. Справочник поясов — база IANA, встроенная в Go (time.LoadLocation); список значений select'а — фиксированный перечень в коде (первые два — «Алматы (UTC+5)», «Москва (UTC+3)»), валидатор принимает любое имя, которое распознаёт time.LoadLocation (DS-033).

§3. Нефункциональные требования

Конкурентность (К-3 — по операциям):

  1. 22Смена своего пояса (PUT /api/v1/users/me/timezone):
    • 23last-write-wins; версия пользователя (version) не проверяется и не увеличивается — DS-033
    • 24as-built: updated_at пользователя обновляется (now()) — D82
  2. 25Правка сотрудника администратором (PUT /api/v1/users/:id):
    • 26механизм как сейчас (as-is, не меняется); timezone отсутствует в теле → колонка не трогается; передан → записывается — DS-056
  3. 27Одновременно сам пользователь и администратор меняют пояс: сохраняется последняя запись — DS-056

Аудит:

  • 28отдельного аудита нет; slog: кто и кому сменил пояс (id, старое → новое значение) — DS-051 (контекст, реализуется в transfers-core)

Время/таймзоны (К-13):

  • 29хранение: UTC, timestamptz — DS-031
  • 30показ: по timezone смотрящего пользователя на всех экранах и в печати — DS-031, DS-032
  • 31текущая дата («сегодня») для подсветки сроков — в поясе пользователя — DS-032
  • 32источник времени: сервер БД (now()); дата печати — time.Now() сервера, переведённая в пояс пользователя
  • 33диапазонов дат в фильтрах в этой части нет (появятся в transfers-partners, DS-034)

Метрики/таймстемпы:

  • 34новых нет

Offline / деградация / восстановление:

  • 35пояс читается с сервера при каждой загрузке страницы; неизвестное браузеру имя пояса → форматтер падает обратно на Asia/Almaty, страница не ломается

Логирование и чувствительные данные:

  • 36чувствительных данных нет

Формат ошибок:

  • 37только pkg/errorspkg: {code, message, details}; 400 → details.fields[]

Abuse cases (вход для adversarial E2E TD-4):

  1. 38Исполнитель пытается сменить чужой пояс через PUT /api/v1/users/:id → 403 (as-is admin-guard).
  2. 39В PUT /api/v1/users/me/timezone передан user_id чужого пользователя → игнорируется, меняется пояс владельца сессии.
  3. 40timezone = ../../etc/passwd, строка в 10 000 символов, Mars/Olympus → 400, запись не изменена.
  4. 41Запрос без сессии → 401.

Применённые zap-дефолты (zap-list — стандарты проекта из CLAUDE.md, применяются автоматически, без вопросов; в §9 — источник zap):

§6. API

Режим B «API + фронтенд». Базовый URL стенда: http://localhost:8080. Авторизация — сессионная cookie sid (плейсхолдер <SID>). Копируй curl в терминал или в Postman: Import → Raw text. Тело ошибки — формат pkg/errorspkg: {code, message, details}; при 400 — details.fields[] с name и message. Ключи — snake_case, URL — kebab-case (CLAUDE.md §API-1).

§6.1. PUT /api/v1/users/me/timezone

  • 66Назначение: пользователь меняет свой часовой пояс.
  • 67Authz: любой авторизованный — только себе; id пользователя берётся из сессии, в теле не принимается — DS-033. Чужой пояс этим endpoint'ом не изменить; администратор меняет пояс любому пользователю через PUT /api/v1/users/:id (§6.2) — DS-056.
  • 68Идемпотентность/повтор: безопасен; last-write-wins.
  • 69Side effects: users.timezone и users.updated_at (as-built, D82; version не меняется); GET /api/v1/auth/me и SSR-layout начинают отдавать новое значение со следующего запроса (значение читается из БД/сессии на каждый запрос — устаревший пояс в кэше сессии недопустим).
