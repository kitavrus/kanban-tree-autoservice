Swimlane: Доска заказов и Остатки

Фаза 5 — управление заказами через колонки (Kanban), транзакционное списание товаров со склада, прогноз остатков

Цели: Kanban-доска с перемещением заказов между колонками с дробной позицией; автоматическое списание товаров при смене статуса; инвариант склада при гонках и откатах; экран «Остатки» с прогнозом по незавершённым заказам; KPI рисковых товаров с бейджем в меню.

Ключевые потоки данных

AC-001: Загрузка доски (GET /api/v1/columns + GET /api/v1/tasks)
GET /api/v1/columns (любой) → ColumnListResponse; GET /api/v1/tasks?client_id&q&paid&due&assignee&limit=500&offset=0 → TaskListResponse
Columns (ответ):
  • id, name, position, color, consumes_stock, is_final, tasks_count
Tasks (TaskCard, см. design-go-layers.md):
  • id (bigserial), column_id, title, client_id, client_name, assignee_id, assignee_name, due_date, is_paid, version, subtasks_total, subtasks_done, subtasks_late
  • position (numeric строкой для отладки/сортировки)
AC-002/AC-004/AC-005: Перенос заказа между колонками (POST /api/v1/tasks/:id/move)
POST /api/v1/tasks/:id/move (любой) → 200 TaskMutationResponse | 409 SUBTASKS_NOT_DONE | 400
Request (ADR-001: дробная позиция):
  • column_id (uuid, целевая колонка)
  • prev_id (int64 | null, задача выше; может быть из другой колонки → игнорируется)
  • next_id (int64 | null, задача ниже)
Валидация и рассчёт позиции:
  • Проверка D11: если target column is_final AND есть незавершённые услуги (subtask.status<>'done') → 409 SUBTASKS_NOT_DONE + details.subtasks[{id, service_name, status}]
  • Position: trim_scale((prev.position + next.position) / 2) или edge-case (только prev, только next, ни одного)
  • Ребалансировка при scale>20: UPDATE tasks SET position=row_number()*1024 WHERE column_id=target
Reconcile (ADR-004, D17/D34):
  • Определить old_consumes, new_consumes по старой и новой column.consumes_stock
  • Для каждого product в subtasks заказа: dq = old_consumes ? −qty : +qty; new_dq = new_consumes ? −qty : +qty
  • INSERT stock_movements (reason=task_consume, qty_delta=dq) + UPDATE task_stock, products.stock
Response (warnings, ADR-006):
  • warnings: [{product_id, name, stock (после изменения), min_stock, kind: 'negative'|'below_min'}]
  • Только товары, где qty_delta≠0; negative = stock<0, below_min = 0≤stock≤min_stock
AC-003: Проверка незавершённых услуг перед финальной колонкой (D11, D22)
POST /tasks/:id/move → 409 SUBTASKS_NOT_DONE {details: {subtasks: [{id, service_name, status}]}}
Логика (ADR-102: Extra в errorspkg):
  • SELECT s.id, sv.name AS service_name, s.status WHERE task_id=id AND status<>'done' → если не пусто И column.is_final, отказ
  • Ошибка содержит Extra.subtasks[] (не Validation fields)
AC-007: Переключение «списывать товары» на колонке (PUT /api/v1/columns/:id с consumes_stock)
PUT /api/v1/columns/:id (Admin) → 200 ColumnMutationResponse + warnings
Действие:
  • UPDATE column SET consumes_stock=true/false
  • SELECT all tasks in column → для каждого вызвать StockEngine.Reconcile
  • Результат: warnings + пересчёт stock для всех заказов в колонке
AC-009: Создание заказа (POST /api/v1/tasks)
POST /api/v1/tasks (любой) → 201 TaskMutationResponse
Request (TaskCreateRequest):
  • title (required, 1..200), client_id (uuid, required), column_id (uuid, required)
  • assignee_id (uuid | null), due_date (YYYY-MM-DD | null), is_paid (bool; executor: null|false, иначе 403 PAID_ADMIN_ONLY)
  • Заказ создаётся в default column (или указанную) с position=max+1024
AC-012: Удаление заказа (DELETE /api/v1/tasks/:id)
DELETE /api/v1/tasks/:id (Admin) → 200 TaskDeleteResponse (со сводкой возвратов)
Действие:
  • Если заказ в consumes_stock колонке, вернуть товары (ADR-004 undo reconciliation)
  • DELETE task_stock, stock_movements (task_id=id), subtasks, DELETE task
AC-015/AC-016: Экран «Остатки» и бейдж (GET /api/v1/stock + GET /stock/summary)
GET /api/v1/stock?scope=all|risky&limit=&offset= → StockListResponse; GET /stock/summary → StockSummaryResponse
Stock Summary (ADR-002: прогноз):
  • pending = Σ subtask_products.qty для заказов в NOT consumes_stock AND NOT is_final колонках
  • forecast = stock − pending
  • states: out (stock≤0), low (0min AND forecast≤min), ok
  • kpi: {out_count, low_count, will_low_count} (для бейджа: risk_count = out+low+will_low)
Stock Table (scope=risky → только state<>'ok'):
  • product_id, name, stock, min_stock, state, forecast, risk_count (бейдж в меню)
  • Сортировка: stock−min_stock ASC (самые критичные сверху)
AC-013/AC-014: Фильтры доски (GET /api/v1/tasks?client_id&q&paid&due&assignee)
Серверная фильтрация, AND-комбинация; дефолт assignee по роли (executor→'me')
Параметры:
  • q: ILIKE по tasks.title / clients.company_name + точный поиск #N (ID заказа)
  • paid: all|paid|unpaid; due: all|soon|overdue
  • assignee: me|all|{uuid}; client_id: {uuid}
AC-017/AC-018: D26-гарды на удаление клиента и оборудования
DELETE /api/v1/clients/:id → 409 CLIENT_HAS_TASKS; DELETE /api/v1/equipment/:id → 409 EQUIPMENT_USED_IN_TASKS
Логика (ADR-005: гарда в clients/catalog без импорта board):
  • clients.DeleteClient: SELECT COUNT(*) FROM tasks WHERE client_id=id → если >0, 409
  • catalog.equipment.DeleteEquipment: SELECT COUNT(*) FROM subtasks WHERE equipment_id=id OR FROM task_equipment → если >0, 409
Обработка ошибок и warnings
Коды 400 (валидация), 409 (конфликт состояния), 404 (IDOR), 403 (роль/PAID_ADMIN_ONLY)
Sentinel-коды (design-errors.md):
  • SUBTASKS_NOT_DONE (409) — попытка перейти в финальную колонку с незавершёнными услугами + Extra.subtasks[]
  • TASK_VERSION_CONFLICT (409) — PUT с неверной version
  • CLIENT_HAS_TASKS (409) — попытка удалить клиента с заказами
  • EQUIPMENT_USED_IN_TASKS (409) — попытка удалить оборудование из заказа
  • PAID_ADMIN_ONLY (403) — executor меняет is_paid
  • Warnings: [{product_id, name, stock, min_stock, kind: 'negative'|'below_min'}] — не ошибка, move выполняется
AC-019: Seed demo (make seed-demo, ADR-105)
Заполнение БД демо-данными (клиенты, оборудование, услуги, заказы во всех колонках, товары, остатки)
Действие:
  • Guard: SELECT COUNT(*) FROM tasks → если >0, exit 0 (уже есть данные)
  • TX: вставка clients, equipment, services, products, columns, tasks, subtasks, stock_movements
  • Reconcile для всех заказов в consumes_stock колонках → инвариант склада сходится
Инвариант склада (Stock Invariant)
Проверка консистентности: sum(stock_movements.qty_delta) = task_stock.qty для каждой (task_id, product_id)
Выполняется при:
  • Каждом move (Reconcile идемпотентен)
  • PUT stock (manual adjustment)
  • DELETE task (возврат товаров)
  • toggle consumes_stock на колонке (ребалансировка всех заказов)
