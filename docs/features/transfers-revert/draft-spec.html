После мержа этой части мастер-спека реализована полностью: администратор может «Отменить проведение» полученного документа любого направления (документ возвращается в «В пути», остатки и местоположение откатываются), удалить документ в статусе «Заявка» или «Отменён»; заказ с неоткатанными документами не удаляется, и сообщение называет мешающие документы, а отменённые документы удаляются вместе с заказом. §1. Суть задачи

Исправление ошибочно проведённых документов и правила удаления до появления мягкого удаления. Для администратора.

Бизнес (что делает пользователь/процесс):

  1. 1Администратор нажимает «Отменить проведение» у полученного документа и указывает причину — документ возвращается в «В пути», дальше его можно принять заново с верным фактом либо отменить (§8.1) — DS-017.
  2. 2Удаляет документ, не влияющий на учёт: «Заявка» или «Отменён» (§8.1) — DS-025.
  3. 3При удалении заказа видит, какие документы мешают; после их отката и отмены заказ удаляется (§8.2) — DS-025.

Логика (правила системы):

  1. 4«Получено» перестаёт быть окончательным: переход received → in_transit, только администратор, обязательная причина 1–500 символов (пересмотр D51) — DS-017, DS-053.
  2. 5Откат — в обратном порядке: документ не отменить, пока его единицу оборудования увёз более поздний документ либо она стоит в другом незавершённом; система называет мешающий документ — DS-023.
  3. 6Учётные причины откат не блокируют: товар успели израсходовать — остаток уходит в минус с предупреждением; заказ отмечен «Оплачен» — накладная откатывается, отметка остаётся — DS-020, DS-023.
  4. 7Что откатывается: остаток — компенсирующим движением transfer_unreceive на факт приёмки; единицы — снова «в пути» и заняты этим документом; факт по строкам и отметка «кто/когда принял» обнуляются — DS-017.
  5. 8На документе фиксируется последний откат: кто, когда, причина — DS-044.
  6. 9Удалить документ можно только в requested или cancelled; проведённый сначала откатывают, затем отменяют, затем удаляют — DS-025.
  7. 10Заказ, у которого есть документ в requested, in_transit, received, удалить нельзя; отменённые документы заказа удаляются вместе с ним — DS-025, DS-050.
  8. 11Мягкое удаление с восстановлением и отчёт «Удалённые заказы» — не здесь: отдельная следующая задача — DS-021, DS-022.
  9. 12Время: unreceived_at хранится в UTC, показывается по поясу пользователя (DS-031 — контекст, реализуется в user-timezone); порядок документов для правила «более поздний» — по received_at, при равенстве по id.
  10. 13Конкурентный доступ (краткий дубль §3):
    • 14откат и удаление документа → optimistic lock version + 409 (DS-048 — контекст, реализуется в transfers-core);
    • 15откат остатка → FOR UPDATE строк product_stock склада назначения в порядке product_id;
    • 16откат единиц → guard под FOR NO KEY UPDATE строк equipment (as-built, D75; не FOR UPDATE): единица там, куда её привёз этот документ, свободна, и более позднего документа с ней нет — DS-023;
    • 17удаление заказа → проверка документов и удаление отменённых в одной транзакции с удалением заказа — DS-025 (as-built, D75: документы при этом не блокируются — только заказ).

Техника (API/данные/интеграции):

  1. 18transfers: unreceived_by, unreceived_at, unreceive_reason (§4.1).
  2. 19Новые POST /api/v1/transfers/:id/unreceive, DELETE /api/v1/transfers/:id (§6.1, §6.2).
  3. 20Дельта DELETE /api/v1/tasks/:id: код TASK_HAS_TRANSFERS с номерами документов вместо общего 409 части 4; каскад отменённых (§6.3).
  4. 21Движение transfer_unreceive начинает писаться (значение в CHECK добавлено частью 4).

UI (графическая часть):

  1. 22Документ: кнопка «Отменить проведение» (admin, «Получено») с диалогом причины; кнопка «Удалить» (admin, «Заявка» / «Отменён»); строка «Проведение отменено: кто, когда, причина» (§8.1).
  2. 23Карточка заказа: сообщение со ссылками на документы при попытке удалить заказ (§8.2).

Out-of-scope:

  1. 24Мягкое удаление с восстановлением и отчёт «Удалённые заказы» — отдельная следующая задача (DS-022); после неё запреты удаления этой части пересматриваются.
  2. 25Каскадный откат цепочки документов одним действием — нет: только в обратном порядке, по одному (DS-023).
  3. 26История всех откатов документа — нет: хранится последний (DS-044); более ранние — только в slog.
  4. 27Откат отмены (cancelled → обратно) — нет: отменённый документ терминален, создаётся новый.
  5. 28Возврат проданного товара от клиента — нет (DS-004 — контекст, реализуется в transfers-partners).

§3. Нефункциональные требования

Конкурентность (К-3 — по операциям):

  1. 29Отмена проведения (POST /api/v1/transfers/:id/unreceive):
    • 30optimistic lock: обязательный version, строка transfers FOR UPDATE; устаревшая версия → 409 TRANSFER_VERSION_CONFLICT; статус не received → 409 TRANSFER_STATUS_CONFLICT (DS-048 — контекст, реализуется в transfers-core)
    • 31Lock Order: transfers → строки product_stock склада назначения в порядке product_id → строки equipment в порядке id
    • 32as-built (D75): общий порядок блокировок перемещений — документ (FOR UPDATE) → заказ (FOR KEY SHARE, при создании/правке документа с клиентом) → product_stock (FOR UPDATE, по product_id) → equipment (FOR NO KEY UPDATE, по id)
    • 33единицы: под блокировкой проверяется, что единица числится там, куда её привёз этот документ, active_transfer_id IS NULL и нет более позднего полученного документа с ней; иначе 409 TRANSFER_UNRECEIVE_BLOCKED, ничего не изменено — DS-023
    • 34два одновременных отката одного документа → один 200, второй 409 по версии; компенсирующее движение одно
  2. 35Откат одновременно с новым документом по той же единице: кто первым взял блокировку строки equipment, тот и выиграл; проигравший получает 409 (EQUIPMENT_IN_TRANSFER у создания либо TRANSFER_UNRECEIVE_BLOCKED у отката) — DS-023
  3. 36Удаление документа (DELETE /api/v1/transfers/:id): version + статус под FOR UPDATE; удаление одновременно с отправкой → один успех, второй 409 — DS-025
  4. 37Удаление заказа (DELETE /api/v1/tasks/:id): в транзакции удаления заказ блокируется (существующий LockTask), документы заказа читаются под FOR UPDATE; есть неотменённый → 409, ничего не удалено; иначе отменённые документы и заказ удаляются одной транзакцией — DS-025, DS-050
    • 38as-built (D75): документы заказа читаются БЕЗ FOR UPDATE — порядок «заказ → документ» против «документ → заказ» в правке заявки дал бы взаимную блокировку; гонок нет: создание документа ждёт блокировку заказа (FOR KEY SHARE), «Отменён» терминален, страховка — FK transfers.task_id RESTRICT; отменённые документы удаляет сам board SQL-запросом в транзакции удаления

Аудит:

  • 39на документе: unreceived_by, unreceived_at, unreceive_reason — последний откат — DS-044
  • 40slog: каждый откат (id документа, пользователь, причина) и каждое удаление документа (id, статус, пользователь)
  • 41компенсирующие движения transfer_unreceive в stock_movements с transfer_id; при удалении документа transfer_id движений → NULL (журнал остатков сохраняется)

Время/таймзоны (К-13):

  • 42хранение: UTC, timestamptz; показ — по поясу пользователя
  • 43«более поздний документ» — по received_at, при равенстве по id; время — сервера БД

Метрики/таймстемпы:

  • 44unreceived_at; отчётов и алертов нет

Offline / деградация / восстановление:

  • 45как в ядре; повтор отката или удаления после сбоя сети безопасен: вторая попытка получит 409 либо 404

Логирование и чувствительные данные:

  • 46причина отката — свободный текст пользователя, пишется в slog целиком (до 500 символов); чувствительных данных нет

Формат ошибок:

Abuse cases (вход для adversarial E2E TD-4):

  1. 48Исполнитель вызывает POST /api/v1/transfers/:id/unreceive или DELETE /api/v1/transfers/:id → 403, документ не изменён — DS-018 (контекст), DS-042 (контекст).
  2. 49Причина из пробелов, из 501 символа → 400, документ остаётся «Получено».

§5. Статусная модель

Дельта: «Получено» больше не терминальный; появляется удаление. Что можно в каждом статусе после этой части (всё остальное → 409 TRANSFER_STATUS_CONFLICT):

  • 118requested («Заявка»): править, отправить, отменить, удалить (admin)
  • 119in_transit («В пути»): принять, отменить
  • 120received («Получено»): отменить проведение (admin)
  • 121cancelled («Отменён», терминальный): удалить (admin)
