# Отчёт: transfers-revert — отмена проведения и удаление

Часть 6 из 6 мастер-спеки `transfers` (последняя). Ветка `feat/transfers-revert` (поверх `feat/transfers-sales`), base `c374f1b`, не запушена.

## Что сделано

«Отменить проведение» (`POST /api/v1/transfers/:id/unreceive`, миграция `0017`): администратор возвращает полученный документ в «В пути» с обязательной причиной; остатки и местоположение оборудования откатываются по факту приёмки, сведения об откате остаются на документе. Откат не блокируется ни отрицательным остатком (уходит в минус с предупреждением), ни отметкой «Оплачен» у заказа; единственный запрет — единицу уже увёз более поздний документ (откат в обратном порядке, система называет мешающий документ). Удаление документа (`DELETE /api/v1/transfers/:id`) — только в «Заявка» и «Отменён». Удаление заказа: отменённые документы удаляются вместе с ним, при остальных — 409 `TASK_HAS_TRANSFERS` с номерами мешающих документов. Уборка E2E научена откатывать, отменять и удалять документы перед удалением заказа. Журнал решений `docs/plan.md` дополнен D73–D79.

## Known issues

- **Тест гонки `TestTS012_ParallelUnreceiveVsNewDocument` потенциально нестабилен на нагруженном стенде:** требует, чтобы за 30 итераций встретились оба исхода.
- **D73 и D74 в `docs/plan.md`** про части 1–5 написаны со слов оркестратора, по коду тех частей не сверялись.
- **Отступление от §3 п.4 спеки:** при удалении заказа документы не блокируются `FOR UPDATE` (иначе дедлок с правкой заявки) — D75.
- **Правка кода прошлых частей:** `received_at` в `doReceive` — `clock_timestamp()` вместо `now()` (нужно правилу обратного порядка) — D76.
- Исполнитель на unreceive и DELETE документа получает 403 всегда, включая несуществующий документ (по спеке §6.1, §6.2).
- Диалог причины отката — отдельная Bootstrap-модалка, не `KT.uiDialog`.
- Документы без заказа, созданные E2E (межскладские, приходы от поставщика), уборкой не удаляются.
- LOW без правки: нет CHECK согласованности колонок отката (кто ↔ когда ↔ причина); `version ≥ 1` в теле не проверяется (как у send/receive/cancel); литерал `'cancelled'` в пакете board; пример ответа §6.3 спеки расходится с фактическим `{warnings}`.
- Вне объёма по решению пользователя: мягкое удаление с отчётом «Удалённые заказы»; статус «ждёт поставку».
- Миграции `0014`–`0017` не применялись к общей dev-БД (ломающие; на ней работает сервер из `main`).
- Спека приведена к as-built 2026-10-08 (ветка feat/transfers-followups).
