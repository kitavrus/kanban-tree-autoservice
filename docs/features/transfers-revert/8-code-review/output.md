## Оценка по вопросам оркестратора
1. **Откат — допустимо (дефектов нет).** `repo.go:563-605`: склад→склад и приход — `product_stock −Σqty_received` на складе назначения + `transfer_unreceive −qty_received` по строкам с фактом > 0 (приёмка дала чистый +факт: `transfer_in +sent`, `transfer_loss −(sent−fact)`; излишек поставщика снимается целиком; факт 0 — без движения). Документы с клиентом — движений нет, сумма накладной остаётся (тест TS-013: 1300.30 / is_paid). Единицы: `in_transit`, `warehouse_id NULL`, `active_transfer_id = id` — CHECK `equipment_location_check` выполняется во всех ветках; обратно — штатный `settleEquipment`. Повторная приёмка даёт то же состояние (TS-010: остаток, местоположение, Σ движений = остаток), сведения об откате переживают приёмку и отмену. Дубли товаров в документе запрещены валидатором → асимметрии `sum()` отката и построчного UPDATE приёмки нет.
2. **Обратный порядок — допустимо.** `clock_timestamp()` (repo.go:486) нужен и достаточен: единственный опасный случай — `Create` с `receive:true` (клиент→склад), чья транзакция стартовала раньше приёмки предыдущего документа и ждала блокировку единицы; с `now()` порядок инвертировался бы. Более поздний документ всегда берёт блокировку единицы после коммита предыдущего → `received_at` строго возрастает; равенство невозможно (один документ на транзакцию), тай-брейк по id есть. «Увезли и вернули» — блокируется по порядку (тест). Незавершённый документ мешает через `active_transfer_id` (проверяется первым). Самый поздний документ — верный адрес (у него нет более поздних); при нескольких единицах цепочка сходится за конечное число шагов. Случай без мешающего документа — см. MEDIUM-1 (нет теста).
3. **Конкурентность — допустимо.** Параллельный unreceive — `FOR UPDATE` + версия (тест: 1×200, одно движение). Порядок документ → product_stock (один склад, по product_id) → equipment (по id) соблюдён; чужие документы не блокируются (список «более поздних» читается обычным SELECT после блокировки единиц, READ COMMITTED) → дедлока документ↔документ в цепочке нет. Откат vs создание/отправка/приёмка/отмена по той же единице — сериализуются блокировкой строки `equipment`. Теста гонки нет — MEDIUM-1.
4. **Удаление заказа — отступление от §3 п.4 допустимо.** Гонки нет: создание документа ждёт `LockTask` (`FOR KEY SHARE` в `checkRefs`), «Отменён» терминален, правка заявки падает на статусе до блокировки заказа; незакоммиченная отмена видна как «не отменён» → 409 (консервативно). `transfer_items` — CASCADE, `stock_movements.transfer_id` — SET NULL (тест), единицы отменённого документа уже свободны; FK RESTRICT — страховка. С `FOR UPDATE` был бы реальный дедлок с `transfers.Update`. Дублирование знаний — LOW-4.
5. **Удаление документа — допустимо.** Только `requested`/`cancelled`, версия до статуса, единицы блокируются по id и освобождаются FK SET NULL, движения отвязываются, журнал цел (TS-016, TS-018).
6. **Права — согласовано со спекой, выносить не нужно.** §6.1/§6.2 и abuse case 1: «executor → 403» без оговорок; роль первой не раскрывает существование. Отличие от 404 «чужого направления» остальных эндпоинтов осознанное (там действие исполнителю в принципе доступно).
7. **Миграция — допустимо**, LOW-2.
8. **UI — допустимо.** Отдельная модалка оправдана (ошибка под полем, ссылка, блокировка кнопки; прецедент — модалка приёмки), «Удалить» идёт через `KT.uiDialog`. Кнопки — только admin (`state.isAdmin`), сервер дублирует 403. Строка об откате и «↩» — по §8.1. Отказ удаления заказа в шапке карточки — as-built конвенция (расхождение с «тостом» §8.2 зафиксировать, MEDIUM-2).
9. **E2E-уборка — корректна и безопасна**; рекурсия конечна (LOW-5); область — документы заказа теста (`task_id`) + блокеры по его же единицам, демо не задевает; 2 оставшихся заказа — прежнее поведение (LOW-6); документы без заказа — LOW-7.
10. **seed-demo — согласовано.** +20/−20/+18 через `moveStock` (остаток и журнал синхронны), `unreceived_at` (−4д 2ч) < `received_at` (−4д), version 5 / 2; отменённая заявка единицу не занимает.
11. **Тесты — по существу.** Точные остатки, движения (`reason:склад:дельта`), местоположение `status|склад|active`, версии, «отказ ничего не изменил». `TestDeleteTask_WithTransfers409` заменён более сильным `TestTS017_DeleteTaskWithTransfers`. Пробелы — MEDIUM-1.
