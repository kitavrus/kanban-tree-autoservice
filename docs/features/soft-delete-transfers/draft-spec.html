§1. Суть задачи

Удаление документа «Перемещение» становится восстановимым, а заказ с документами — удаляемым. Для администратора; исполнитель видит пометку «заказ удалён» у документов своих направлений.

Бизнес (что делает пользователь/процесс):

  1. 1Администратор удаляет заявку или отменённый документ с причиной (§8.1) и возвращает его из «Удалённых» (§8.2) — DS-018, DS-020.
  2. 2Администратор удаляет заказ, у которого есть документы в любом статусе (окно и кнопка — часть 1) — DS-006.
  3. 3Любой пользователь со своим доступом к «Перемещениям» видит у документа удалённого заказа бейдж «заказ удалён» и доводит документ до конца: отправить, принять, отменить, откатить (§8.1) — DS-007.

Логика (правила системы):

  1. 4Удаляется только документ, не влияющий на учёт: «Заявка» или «Отменён»; проведённый сначала откатывают и отменяют — DS-018.
  2. 5При удалении заявки её единицы оборудования освобождаются; при восстановлении — занимаются снова; единица уже занята другим незавершённым документом → отказ — DS-018.
  3. 6Остатки и местоположение оборудования не меняются ни при удалении, ни при восстановлении документа или заказа — DS-008.
  4. 7Новый документ по удалённому заказу не создаётся; существующие работают как обычно — DS-007.
  5. 8Удалённый документ не существует для обычных адресов (404), не входит в список, в блок перемещений карточки заказа, в итог заказа, в «в пути» на остатках, в историю оборудования — DS-026, DS-010.
  6. 9Удалённый документ не мешает сменить клиента заказа; если клиента сменили, такой документ восстановить нельзя — DS-040.
  7. 10Время: deleted_at — UTC (timestamptz), показ и фильтр — по поясу пользователя, «ДД.ММ.ГГГГ ЧЧ:ММ» — DS-025 (краткий дубль §3).
  8. 11Конкурентный доступ: удаляем документ → оптимистичная блокировка по version + условие «ещё не удалён»; восстанавливаем → условие «удалён», единицы — под блокировкой строк оборудования; создаём документ по заказу → под блокировкой заказа с проверкой «заказ не удалён» — DS-024 (краткий дубль §3).

Техника (API/данные/интеграции):

  1. 12Данные: три новые колонки в transfers, CHECK и частичный индекс; transfer_items, equipment, tasks не меняются (§4).
  2. 13API: DELETE /api/v1/transfers/:id меняет поведение и формат запроса (§6.1); новый POST /api/v1/transfers/:id/restore (§6.2); дельта существующих адресов документов и заказов, вид transfers в GET /api/v1/deleted и в служебной уборке (§6.3).
  3. 14Пакеты: internal/features/transfers (удаление, восстановление, чтение), internal/features/board (снятие отказа при удалении заказа; читатели документов), internal/features/clients (история оборудования), internal/features/softdelete (вид transfers).
  4. 15Внешних систем нет.

UI (графическая часть):

  1. 16«Перемещения»: кнопка «Удалить» открывает общее окно с причиной; бейдж «заказ удалён» в списке и в документе (§8.1).
  2. 17«Удалённые»: новая вкладка «Перемещения» (§8.2).
  3. 18Окно удаления заказа (часть 1): отказ «Сначала отмените перемещения» больше не приходит (§8.3).

Out-of-scope:

  1. 19Бейджи «удалён» у клиента, поставщика, склада, товара и единицы оборудования внутри документа — части 4, 5, 6 (DS-014); отказ восстановления заявки с удалёнными записями в составе (409 TRANSFER_HAS_DELETED_REFS в таблице ошибок §6.2) начинает срабатывать с этими частями — до них удалённых единиц, товаров, складов и поставщиков не бывает (DS-045).
  2. 20Удаление проведённого документа («В пути», «Получено») — запрещено, как и сейчас (решение пользователя, DS-018).
  3. 21Окончательное удаление — не делаем (решение пользователя, DS-012); физическая уборка — только служебная, для автотестов (DS-038).

§3. Нефункциональные требования

Конкурентность (по операциям):

  1. 24Удаление документа:
    • 25оптимистичная блокировка: UPDATE с условиями version = :version, deleted_at IS NULL, status IN ('requested','cancelled'); не совпала версия → 409 TRANSFER_VERSION_CONFLICT; статус не тот → 409 TRANSFER_STATUS_CONFLICT; уже удалён → 404 TRANSFER_NOT_FOUND — DS-018, DS-024
    • 26у заявки освобождение единиц (equipment.active_transfer_id = NULL) — в той же транзакции, под блокировкой строк equipment (FOR NO KEY UPDATE, as-is порядок «документ → equipment», docs/plan.md D75)
  2. 27Восстановление документа:
    • 28UPDATE с условием deleted_at IS NOT NULL; не удалён → 409 NOT_DELETED
    • 29у заявки: строки equipment её единиц блокируются по возрастанию id; единица с active_transfer_id IS NOT NULL → 409 EQUIPMENT_IN_TRANSFER, транзакция откатывается, документ остаётся удалённым — DS-018
    • 30два администратора восстанавливают две заявки с общей единицей одновременно: первая — 200, вторая — 409 EQUIPMENT_IN_TRANSFER
    • 31восстановление документа одновременно со сменой клиента заказа: восстановление держит на заказе FOR KEY SHARE, смена клиента — FOR UPDATE (as-is LockTask): смена выиграла → 409 TRANSFER_CLIENT_MISMATCH; восстановление выиграло → смена видит действующий документ и получает 409 TASK_CLIENT_LOCKED_BY_TRANSFERS — DS-040
  3. 32Создание документа по заказу одновременно с удалением заказа:

§6. API

Режим B «API + фронтенд». Базовый URL стенда: http://localhost:8080. Авторизация — сессионная cookie sid (плейсхолдер <SID>). Копируй curl в терминал или в Postman: Import → Raw text. Тело ошибки — формат pkg/errorspkg: {code, message, details}; при 400 — details.fields[] с name и message. Все ключи — snake_case, URL — kebab-case (CLAUDE.md §API-1). Текст отказа в доступе единый — «Нет доступа». as-is: DELETE /api/v1/transfers/:id принимает version в query (?version=N) и не принимает тело; часть 2 переносит version в JSON-тело рядом с reason — так же, как у POST /api/v1/transfers/:id/unreceive ({version, reason}) — DS-028.
