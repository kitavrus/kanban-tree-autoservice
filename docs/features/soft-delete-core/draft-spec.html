§1. Суть задачи

Удаление заказа становится восстановимым, появляется раздел «Удалённые» и общее окно удаления с обязательной причиной — основа, на которую части 2–6 навешивают остальные виды записей. Для администратора.

Бизнес (что делает пользователь/процесс):

  1. 1Администратор в карточке заказа нажимает «Удалить заказ», вводит причину — заказ исчезает с доски (§8.3, §8.2) — DS-020.
  2. 2Администратор открывает «Администрирование → Удалённые», видит удалённые заказы: что, почему, кто, когда; ищет и фильтрует по периоду и сотруднику (§8.1) — DS-011.
  3. 3Администратор нажимает «Восстановить» — заказ возвращается на доску в свою колонку со всеми услугами, товарами, записями, вложениями и оборудованием; при нехватке товара видит предупреждение (§8.1) — DS-005.

Логика (правила системы):

  1. 4Удалённый заказ остаётся в базе с отметкой «кто, когда, почему»; хранится бессрочно — DS-012, DS-030.
  2. 5При удалении все товары заказа возвращаются на склад; при восстановлении списываются снова по правилу колонки заказа; нехватка — предупреждение, не отказ — DS-004, DS-005.
  3. 6Удалённый заказ не существует для всех обычных адресов: чтение и любая правка — 404 — DS-010, DS-026.
  4. 7Вложения удалённого заказа (строки и файлы) сохраняются; файл по прямой ссылке не отдаётся — DS-013.
  5. 8Переходные правила до следующих частей: заказ с неотменённым документом перемещения по-прежнему не удаляется; отменённые документы вместе с заказом больше не удаляются; удалённый заказ по-прежнему удерживает клиента, оборудование и колонку от безвозвратного удаления — DS-034, DS-035.
  6. 9Время: deleted_at хранится в UTC (timestamptz); показывается и фильтруется по часовому поясу пользователя, формат «ДД.ММ.ГГГГ ЧЧ:ММ» — DS-025 (краткий дубль §3).
  7. 10Конкурентный доступ: удаляем заказ → под блокировкой строки заказа, условие «ещё не удалён», повтор → 404; восстанавливаем → под той же блокировкой, условие «удалён», повтор → 409 — DS-024 (краткий дубль §3).

Техника (API/данные/интеграции):

  1. 11Данные: три новые колонки в tasks (deleted_at, deleted_by, delete_reason), CHECK и частичный индекс; новых таблиц нет (§4.1).
  2. 12API: DELETE /api/v1/tasks/:id меняет поведение (§6.1); новые POST /api/v1/tasks/:id/restore (§6.2), GET /api/v1/deleted (§6.3), GET /api/v1/deleted/summary (§6.4), служебный DELETE /api/v1/test/purge/:kind/:id (§6.5); условие «не удалён» во всех читателях заказов (§6.6).
  3. 13Новый пакет internal/features/softdelete — чтение раздела «Удалённые» и страница /deleted; удаление и восстановление заказа остаются в пакете board.
  4. 14Общие для частей 2–6 заготовки: валидатор причины, коды NOT_DELETED, окно удаления с причиной в KT.uiDialog, реестр видов записей раздела «Удалённые».
  5. 15Внешних систем нет.

UI (графическая часть):

  1. 16Новый пункт меню «Администрирование → Удалённые» (/deleted, только admin) — страница с вкладкой «Заказы», фильтрами, кнопкой «Восстановить» (§8.1).
  2. 17Общее окно «Удаление» с обязательным полем «Причина» (§8.2).
  3. 18Карточка заказа: «Удалить заказ» открывает окно с причиной (§8.3).

Out-of-scope:

  1. 19Удаление и восстановление документов перемещения, пометка «заказ удалён», снятие отказа TASK_HAS_TRANSFERS — часть 2 soft-delete-transfers (DS-006, DS-007, DS-018).
  2. 20Колонки доски и подмена удалённой колонки при восстановлении заказа — часть 3 soft-delete-board-columns (DS-016, DS-019).
  3. 21Клиенты, оборудование, пометки «удалён» в карточке заказа — часть 4 soft-delete-clients (DS-014, DS-015).
  4. 22Каталог и типы оборудования — часть 5; склады и поставщики — часть 6 (DS-009, DS-017, DS-021).
  5. 23Части заказа (услуга, товар в услуге, запись, вложение, оборудование в заказе) — удаляются как сейчас, безвозвратно (решение пользователя, DS-002).
  6. 24Окончательное удаление и очистка по сроку — не делаем (решение пользователя, DS-012).

§6. API

Режим B «API + фронтенд». Базовый URL стенда: http://localhost:8080. Авторизация — сессионная cookie sid (плейсхолдер <SID>). Копируй curl в терминал или в Postman: Import → Raw text.
