## §1. Суть задачи
Удаление заказа становится восстановимым, появляется раздел «Удалённые» и общее окно удаления с обязательной причиной — основа, на которую части 2–6 навешивают остальные виды записей. Для администратора.

**Бизнес (что делает пользователь/процесс):**
1. Администратор в карточке заказа нажимает «Удалить заказ», вводит причину — заказ исчезает с доски (§8.3, §8.2) — DS-020.
2. Администратор открывает «Администрирование → Удалённые», видит удалённые заказы: что, почему, кто, когда; ищет и фильтрует по периоду и сотруднику (§8.1) — DS-011.
3. Администратор нажимает «Восстановить» — заказ возвращается на доску в свою колонку со всеми услугами, товарами, записями, вложениями и оборудованием; при нехватке товара видит предупреждение (§8.1) — DS-005.

**Логика (правила системы):**
1. Удалённый заказ остаётся в базе с отметкой «кто, когда, почему»; хранится бессрочно — DS-012, DS-030.
2. При удалении все товары заказа возвращаются на склад; при восстановлении списываются снова по правилу колонки заказа; нехватка — предупреждение, не отказ — DS-004, DS-005.
3. Удалённый заказ не существует для всех обычных адресов: чтение и любая правка — 404 — DS-010, DS-026.
4. Вложения удалённого заказа (строки и файлы) сохраняются; файл по прямой ссылке не отдаётся — DS-013.
5. Переходные правила до следующих частей: заказ с неотменённым документом перемещения по-прежнему не удаляется; отменённые документы вместе с заказом больше не удаляются; удалённый заказ по-прежнему удерживает клиента, оборудование и колонку от безвозвратного удаления — DS-034, DS-035.
6. Время: `f:deleted_at` хранится в UTC (`timestamptz`); показывается и фильтруется по часовому поясу пользователя, формат «ДД.ММ.ГГГГ ЧЧ:ММ» — DS-025 (краткий дубль §3).
7. Конкурентный доступ: удаляем заказ → под блокировкой строки заказа, условие «ещё не удалён», повтор → 404; восстанавливаем → под той же блокировкой, условие «удалён», повтор → 409 — DS-024 (краткий дубль §3).

**Техника (API/данные/интеграции):**
1. Данные: три новые колонки в `t:tasks` (`f:deleted_at`, `f:deleted_by`, `f:delete_reason`), CHECK и частичный индекс; новых таблиц нет (§4.1).
2. API: `e:DELETE /api/v1/tasks/:id` меняет поведение (§6.1); новые `e:POST /api/v1/tasks/:id/restore` (§6.2), `e:GET /api/v1/deleted` (§6.3), `e:GET /api/v1/deleted/summary` (§6.4), служебный `e:DELETE /api/v1/test/purge/:kind/:id` (§6.5); условие «не удалён» во всех читателях заказов (§6.6).
3. Новый пакет `internal/features/softdelete` — чтение раздела «Удалённые» и страница `/deleted`; удаление и восстановление заказа остаются в пакете `board`.
4. Общие для частей 2–6 заготовки: валидатор причины, коды `NOT_DELETED`, окно удаления с причиной в `KT.uiDialog`, реестр видов записей раздела «Удалённые».
5. Внешних систем нет.

**UI (графическая часть):**
1. Новый пункт меню «Администрирование → Удалённые» (`/deleted`, только admin) — страница с вкладкой «Заказы», фильтрами, кнопкой «Восстановить» (§8.1).
2. Общее окно «Удаление» с обязательным полем «Причина» (§8.2).
3. Карточка заказа: «Удалить заказ» открывает окно с причиной (§8.3).

Out-of-scope:
1. Удаление и восстановление документов перемещения, пометка «заказ удалён», снятие отказа `TASK_HAS_TRANSFERS` — часть 2 `soft-delete-transfers` (DS-006, DS-007, DS-018).
2. Колонки доски и подмена удалённой колонки при восстановлении заказа — часть 3 `soft-delete-board-columns` (DS-016, DS-019).
3. Клиенты, оборудование, пометки «удалён» в карточке заказа — часть 4 `soft-delete-clients` (DS-014, DS-015).
4. Каталог и типы оборудования — часть 5; склады и поставщики — часть 6 (DS-009, DS-017, DS-021).
5. Части заказа (услуга, товар в услуге, запись, вложение, оборудование в заказе) — удаляются как сейчас, безвозвратно (решение пользователя, DS-002).
6. Окончательное удаление и очистка по сроку — не делаем (решение пользователя, DS-012).

## §3. Нефункциональные требования

**Конкурентность (по операциям):**
1. **Удаление заказа:**
   - под блокировкой строки заказа (`LockTask`, `FOR UPDATE` — та же, что у действующего удаления и правки); UPDATE с условием `deleted_at IS NULL`; заказ уже удалён либо не существует → 404 `TASK_NOT_FOUND` — DS-024
   - два администратора удаляют один заказ одновременно: первый — 200, второй — 404; возврат товара выполняется один раз; причина второго не записывается
   - возврат товара — в той же транзакции; порядок блокировок «заказ → `t:product_stock`» не меняется (`docs/plan.md` D75) — DS-004
2. **Восстановление заказа:**
   - под той же блокировкой; UPDATE с условием `deleted_at IS NOT NULL`; заказ не удалён → 409 `NOT_DELETED`; повторное списание товара — в той же транзакции — DS-005, DS-024
3. **Правка заказа одновременно с удалением:**
   - правка ждёт блокировку заказа и после удаления получает 404 `TASK_NOT_FOUND`; правка, прошедшая раньше, сохраняется, заказ удаляется уже изменённым — DS-026
4. **Создание документа перемещения по заказу одновременно с удалением заказа:**
   - без изменений в части 1: создание документа держит на заказе `FOR KEY SHARE` (as-is); документ, созданный раньше удаления, делает удаление невозможным (409 `TASK_HAS_TRANSFERS`); проверка «заказ не удалён» при создании документа — часть 2 — DS-034
5. **Версионирование:** `f:version` заказа при удалении и восстановлении не передаётся и не проверяется (as-is удаление заказа без версии); при обеих операциях `f:version` увеличивается на 1 и `f:updated_at` = `now()` — DS-024

**Аудит:**
- на заказе хранится последнее удаление: `f:deleted_by`, `f:deleted_at`, `f:delete_reason`; читается в разделе «Удалённые» — DS-030
- при восстановлении три поля очищаются; история повторных удалений не ведётся
- факт удаления и восстановления — в журнал приложения (`slog`, info: вид записи, номер, пользователь, действие); причина в журнал не пишется
- чтение раздела «Удалённые» не журналируется

**Время/таймзоны:**
- хранение: `f:deleted_at` — `timestamptz`, UTC, время сервера базы (`now()`) — DS-025
- период фильтра «Удалено с / по» — по часовому поясу пользователя (`pkg/timezone`): день = с 00:00 до 24:00 в поясе пользователя — DS-025
- показ — «ДД.ММ.ГГГГ ЧЧ:ММ» в поясе пользователя (`KT.time`)
- порядок списка — `f:deleted_at` по убыванию, при равенстве — `f:id`

**Метрики/таймстемпы:**
- единственный новый таймстемп — `f:deleted_at`; отчётов по длительностям и оповещений нет
- счётчик вкладки — `e:GET /api/v1/deleted/summary` (§6.4)

**Offline / деградация / восстановление:**
- удаление и восстановление — одиночные запросы; при потере связи кнопка разблокируется, тост ошибки, повтор безопасен (см. «Идемпотентность» в §6)
- перезагрузка страницы «Удалённые» восстанавливает вкладку, фильтры и страницу списка из адресной строки

**Объёмы и производительность:**
- удалённое копится бессрочно (DS-012): список — серверная пагинация (`limit` по умолчанию 50, максимум 200), частичный индекс `i:tasks_deleted_at_idx`
- условие `deleted_at IS NULL` в запросах доски использует существующие индексы `i:tasks_column_position_idx`, `i:tasks_client_id_idx`, `i:tasks_assignee_id_idx` (доля удалённых мала)

**Логирование и чувствительные данные:**
- причина удаления — свободный текст, в журнал приложения не пишется
- раздел «Удалённые» и его API — только администратору — DS-003

**Формат ошибок:**
- `pkg/errorspkg`: `{code, message, details}`; 400 → `details.fields[]` с `name` и `message`; отказ в доступе — 403 «Нет доступа»

**Abuse cases (инсайдерские риски — вход для adversarial E2E TD-4):**
1. Исполнитель вызывает `DELETE /api/v1/tasks/:id`, `POST /api/v1/tasks/:id/restore`, `GET /api/v1/deleted`, `GET /api/v1/deleted/summary` напрямую → 403 «Нет доступа» до любого чтения записи — DS-003.
2. Исполнитель открывает карточку, печатную форму или вложение удалённого заказа по прямой ссылке → 404, как для несуществующего — DS-010, DS-013.
3. Причина удаления из пробелов или длиннее 500 символов → 400 — DS-020.
4. Служебная уборка вызвана на стенде без `TEST_PURGE_ENABLED=true` → 404, адрес не зарегистрирован — DS-027.
5. Перебор `kind` и `id` в служебной уборке исполнителем → 403 — DS-027.

**Применённые zap-дефолты** (zap-list — стандарты проекта из CLAUDE.md, применяются автоматически, без вопросов; в §9 — источник `zap`):
- коды ответов: 404 — не найдено, 403 — нет доступа, 409 — конфликт состояния (zap)
- обработка синхронная, очередей нет (zap)
- отдельной таблицы аудита нет — отметка на записи и журнал приложения (zap)
- миграции применяются вручную (`make migrate-up`) (zap)

## §4. Данные
Легенда колонки «Обяз.»: `да` — клиент обязан передать при создании/правке; `нет` — опционально; `авто` — заполняет система (PK, дефолты, таймстемпы, значения из URL/сессии); `условно` — зависит от правила, оно указано в Описании. NULL — DDL-факт, Обяз. — семантика заполнения.

### §4.1. `t:tasks` (существующая таблица — фича добавляет колонки миграцией ALTER, созданием не владеет)

Ключи и индексы:
- PK: `f:id` (as-is)
- UNIQUE: нет (as-is)
- Индексы (as-is): `i:tasks_column_position_idx` (`column_id`, `position`, `id`) — доска; `i:tasks_client_id_idx` (`client_id`) — заказы клиента; `i:tasks_assignee_id_idx` (`assignee_id`) — заказы сотрудника
- Индексы (новое): `i:tasks_deleted_at_idx` (`deleted_at DESC`, `id`) `WHERE deleted_at IS NOT NULL` — список вкладки «Заказы» раздела «Удалённые» с сортировкой по времени удаления (§6.3)
- CHECK (новое) `i:tasks_deleted_chk`: `f:deleted_at`, `f:deleted_by`, `f:delete_reason` либо все NULL, либо все заполнены; `char_length(btrim(delete_reason))` от 1 до 500 — DS-030, DS-020

Связи (одна связь = одна строка):
- N→1 `t:columns` — RESTRICT (as-is) — удалённый заказ удерживает колонку от безвозвратного удаления до части 3 (DS-035)
- N→1 `t:clients` — RESTRICT (as-is) — удалённый заказ удерживает клиента от безвозвратного удаления до части 4 (DS-035)
- N→1 `t:users` (`f:assignee_id`) — SET NULL (as-is)
- N→1 `t:users` (`f:created_by`) — RESTRICT (as-is)
- N→1 `t:users` (`f:deleted_by`) — RESTRICT (новое)
- 1→N `t:subtasks` — CASCADE (as-is) — строки остаются, пока заказ в удалённых (DS-002)
- 1→N `t:task_stock` — CASCADE (as-is) — после удаления заказа пусто: товары возвращены (DS-004)
- 1→N `t:task_equipment` — CASCADE (as-is) — строки остаются
- 1→N `t:task_attachments` — CASCADE (as-is) — строки и файлы остаются (DS-013)
- 1→N `t:transfers.task_id` — RESTRICT (as-is) — отменённые документы остаются у удалённого заказа (DS-034)
- 1→N `t:stock_movements.task_id` — SET NULL (as-is) — при мягком удалении ссылка сохраняется

Поведение при действиях (одно действие = одна строка):
- Создание: без изменений (as-is); три поля удаления — NULL
- Изменение: без изменений для действующего заказа; удалённый заказ → 404 `TASK_NOT_FOUND` на любую правку заказа и его частей — DS-026
- Удаление: только admin, причина обязательна; одна транзакция под блокировкой заказа: проверка документов (неотменённые → 409 `TASK_HAS_TRANSFERS`, DS-034) → возврат всех товаров на склад (`StockEngine.Reconcile(false)`, движения `task_return`) → запись `f:deleted_at`, `f:deleted_by`, `f:delete_reason`; строка и все части заказа остаются; файлы вложений не трогаются — DS-004, DS-013, DS-020
- Восстановление: только admin; одна транзакция под блокировкой заказа: очистка трёх полей → если колонка заказа стала финальной, а у заказа есть незавершённые услуги, заказ переносится в конец первой нефинальной колонки (DS-039) → `StockEngine.Reconcile(consumes_stock колонки заказа)` — товары списываются снова, если колонка списывает; нехватка → предупреждения в ответе, не отказ — DS-005
- Физическое удаление: только служебная уборка автотестов (§6.5) — DS-027, DS-036

Инварианты (правило → чем держится → DS):

## §5. Статусная модель
Статусная диаграмма не рисуется: в части 1 у заказа два состояния (общая диаграмма с архивом — в мастере, `docs/features/soft-delete/draft-spec-status.svg`). Колонка доски как статус заказа не меняется.

Состояния: `s:active` — заказ действует (`deleted_at IS NULL`); `s:deleted` — заказ удалён (`deleted_at IS NOT NULL`). Терминальных состояний нет — DS-012.

| Из | В | Триггер | Кто | Guard / конкурентный исход | Side effects |
|---|---|---|---|---|---|
| `s:active` | `s:deleted` | «Удалить заказ» + причина | admin | под блокировкой заказа, `deleted_at IS NULL`; нет неотменённых документов (иначе 409 `TASK_HAS_TRANSFERS`); второй запрос → 404 | возврат товаров на склад |
| `s:deleted` | `s:active` | «Восстановить» | admin | под блокировкой заказа, `deleted_at IS NOT NULL`; второй запрос → 409 `NOT_DELETED` | повторное списание товаров по правилу колонки; предупреждения при нехватке; подмена колонки, ставшей финальной (DS-039) |

Что можно в `s:deleted`: только «Восстановить» и просмотр в разделе «Удалённые»; всё остальное → 404 — DS-026.

## §6. API
> Режим B «API + фронтенд». Базовый URL стенда: `http://localhost:8080`. Авторизация — сессионная cookie `sid` (плейсхолдер `<SID>`). Копируй curl в терминал или в Postman: Import → Raw text. Тело ошибки — формат `pkg/errorspkg`: `{code, message, details}`; при 400 — `details.fields[]` с `name` и `message`. Все ключи — snake_case, URL — kebab-case (CLAUDE.md §API-1). Текст отказа в доступе единый — «Нет доступа».
> Единые правила (DS-028): удаление — `DELETE /api/v1/{ресурс}/:id` с JSON-телом `{reason}`; восстановление — `POST /api/v1/{ресурс}/:id/restore` без тела; список удалённого — `GET /api/v1/deleted`.

### §6.1. `e:DELETE /api/v1/tasks/:id`
- Назначение: мягко удалить запись «заказ» — она уходит в раздел «Удалённые» (существующий адрес, раньше удалял безвозвратно). Часть 1 `soft-delete-core`.
- Authz: только admin; executor → 403 «Нет доступа»; роль проверяется первой, до поиска записи — DS-003.
- Идемпотентность/повтор: повтор удаления уже удалённой записи → 404 (удалённая запись для обычных адресов не существует, DS-026); двойное применение невозможно — UPDATE с условием `deleted_at IS NULL` (DS-024).
- Side effects: одна транзакция под блокировкой заказа — `t:task_stock`, `t:product_stock`, `t:stock_movements` (возврат товаров, `task_return`), затем три поля удаления `t:tasks`; файлы вложений не трогаются (DS-013); документы перемещения заказа не удаляются и не меняются, в том числе отменённые (раньше отменённые удалялись вместе с заказом) — DS-034.

Request:

| Параметр | Где | Тип | Обязателен | Валидация |
|---|---|---|---|---|
| `f:id` | path | integer | да | существующая действующая запись; иное → 404 |
| `f:reason` | body | string | да | 1–500 символов после обрезки крайних пробелов; пусто → 400 `required`; длиннее → 400 `too_long`; недопустимые символы (NUL) → 400 `invalid_text` |

Response 200:

| Поле | Тип | Описание |
|---|---|---|
| `f:id` | integer | идентификатор удалённой записи |
| `f:deleted_at` | string (RFC 3339, UTC) | момент удаления |
| `f:warnings` | array | предупреждения по остатку после возврата товаров на склад — действующий формат ответа удаления заказа (as-is `TaskDeleteResponse`); пустой массив, если предупреждений нет |

Ошибки:

| Код | Условие | Сообщение пользователю |
|---|---|---|
| 400 `VALIDATION` | `reason: required` | «Укажите причину удаления» |
| 400 `VALIDATION` | `reason: too_long` | «Причина — не длиннее 500 символов» |
| 400 `VALIDATION` | `reason: invalid_text` | «Недопустимые символы в причине» |
| 403 `FORBIDDEN` | executor | «Нет доступа» |
| 404 `TASK_NOT_FOUND` | записи нет либо она уже удалена | «Заказ не найден» |
| 409 `TASK_HAS_TRANSFERS` | у заказа есть документ в `s:requested`, `s:in_transit`, `s:received` — действующий отказ, остаётся до части 2 `soft-delete-transfers` (`details.transfer_ids` — номера по возрастанию) | «Сначала отмените перемещения: #N, #M» |

Успех:
```bash
curl -s -b 'sid=<SID>' -X DELETE 'http://localhost:8080/api/v1/tasks/128' \
  -H 'Content-Type: application/json' -d '{"reason":"Создан по ошибке"}'
```
```json
{ "id": 128, "deleted_at": "2026-10-08T09:15:42Z", "warnings": [] }
```
Ошибка (VALIDATION → 400):
```bash

  -H 'Content-Type: application/json' -d '{"reason":"  "}'
```
```json
{
  "code": "VALIDATION",
  "message": "validation failed",
  "details": { "fields": [ { "name": "reason", "message": "required" } ] }
}
```
DS: DS-004, DS-020, DS-003, DS-024, DS-026, DS-028, DS-034.

### §6.2. `e:POST /api/v1/tasks/:id/restore`
- Назначение: восстановить удалённую запись «заказ» из раздела «Удалённые» (новый адрес). Часть 1 `soft-delete-core`.

- Идемпотентность/повтор: повтор восстановления действующей записи → 409 `NOT_DELETED`; двойное применение невозможно — UPDATE с условием `deleted_at IS NOT NULL` (DS-024).
- Side effects: одна транзакция под блокировкой заказа — очистка трёх полей удаления; если колонка заказа стала финальной, а у заказа есть незавершённые услуги, — новые `f:column_id` и `f:position` (DS-039); затем `t:task_stock`, `t:product_stock`, `t:stock_movements` (повторное списание, `task_consume`, если колонка списывает товар).

| Параметр | Где | Тип | Обязателен | Валидация |
|---|---|---|---|---|
| `f:id` | path | integer | да | существующая запись (удалённая); иное → 404 |

Тела запроса нет.

| Поле | Тип | Описание |

### §6.3. `e:GET /api/v1/deleted`

### §6.5. `e:DELETE /api/v1/test/purge/:kind/:id`
- Назначение: служебная физическая уборка тестовых заказов автотестами — замена безвозвратного `DELETE /api/v1/tasks/:id`, на который опиралась уборка `adminApi.purgeTask`. В продукте окончательного удаления нет (DS-012). В части 1 поддержан только вид `s:tasks`.
- Authz: только admin; executor → 403 «Нет доступа».
- Спец-механика: адрес регистрируется только при переменной окружения `TEST_PURGE_ENABLED=true`; по умолчанию выключен — адреса нет, ответ 404 — DS-027.
- Идемпотентность/повтор: повтор → 404.
- Side effects: поведение действующего безвозвратного удаления заказа (as-is `TaskService.Delete`), одна транзакция под блокировкой заказа: неотменённые документы → отказ; отменённые документы удаляются; возврат товаров на склад (для действующего заказа; у удалённого товар уже возвращён); физическое удаление строки `t:tasks` (части заказа — каскадом); после commit — файлы вложений с диска. Работает и для действующего, и для мягко удалённого заказа — DS-036.

Request:

| Параметр | Где | Тип | Обязателен | Валидация |
|---|---|---|---|---|
| `f:kind` | path | string | да | в части 1 — только `s:tasks`; иное → 404 |
| `f:id` | path | string | да | номер заказа (действующего или удалённого); не число либо нет заказа → 404 |

Response 200:

| Поле | Тип | Описание |
|---|---|---|
| `f:id` | string | номер физически удалённого заказа |

Ошибки:

| Код | Условие | Сообщение пользователю |
|---|---|---|
| 403 `FORBIDDEN` | executor | «Нет доступа» |
| 404 `NOT_FOUND` | уборка выключена, вид не `s:tasks` либо заказа нет | «Не найдено» |
| 409 `TASK_HAS_TRANSFERS` | у заказа есть документ в `s:requested`, `s:in_transit`, `s:received` (автотест сначала отменяет и удаляет документы — as-is `purgeTask`) | «Сначала отмените перемещения: #N, #M» |

Успех:
```bash
curl -s -b 'sid=<SID>' -X DELETE 'http://localhost:8080/api/v1/test/purge/tasks/128'
```
```json
{ "id": "128" }
```
Ошибка (NOT_FOUND → 404):
```bash
curl -s -b 'sid=<SID>' -X DELETE 'http://localhost:8080/api/v1/test/purge/tasks/999999'
```
```json
{
  "code": "NOT_FOUND",
  "message": "Не найдено"
}
```
DS: DS-027, DS-036.

### §8.1. Экран/форма «Удалённые»

**Как попадаем:**
- **Путь:** меню «Администрирование → Удалённые» (новый пункт, только admin)
- **URL:** `/deleted?kind=tasks&q=&deleted_from=&deleted_to=&deleted_by=&offset=0`
- **Роли:** admin; executor — страница отказа «Нет доступа» · **Устройство:** десктоп; телефон — без горизонтальной прокрутки страницы (таблица прокручивается внутри своего блока)
- **При открытии:** `GET §6.4` → `/api/v1/deleted/summary`, затем `GET §6.3` → `/api/v1/deleted?kind=tasks&limit=50&offset=0`
- **200:** вкладки со счётчиками и таблица выбранной вкладки · **Пусто:** «Удалённых записей нет» · **4xx:** тост с текстом ошибки, таблица пустая

**Что на странице (сверху вниз):**
1. Заголовок «Удалённые».
2. Вкладки (Bootstrap `nav-tabs`), у каждой — счётчик в скобках; в части 1 вкладка одна, остальные добавляют части 2–6:
   - «Заказы» (`s:tasks`)
3. Панель фильтров (под вкладками, в одну строку; сочетание — «И»; кнопка «Сбросить» справа очищает все четыре):

   | Фильтр | Контрол | Источник значений | API-параметр §6.3 | Пример |
   |---|---|---|---|---|
   | Поиск | текст-поиск | ввод пользователя | `f:q` | «кофемашина» |
   | Удалено с | date | ввод пользователя, день в поясе пользователя | `f:deleted_from` | 01.10.2026 |
   | Удалено по | date | ввод пользователя, день в поясе пользователя | `f:deleted_to` | 08.10.2026 |
   | Кто удалил | select | активные сотрудники с ролью admin из `e:GET /api/v1/assignees` (существующий адрес; неактивных сотрудников в списке нет — их удаления находятся поиском и периодом) | `f:deleted_by` | «Анна Смирнова» |

4. Блок предупреждений (жёлтый, появляется после восстановления заказа с предупреждениями).
5. Таблица, колонки слева направо:
   - «Что удалено» (`f:title` — «#128 Ремонт кофемашины»; под ним мелким шрифтом `f:subtitle` — имя клиента)
   - «Причина» (`f:delete_reason`, длинный текст переносится)
   - «Кто удалил» (`f:deleted_by.name`)
   - «Когда» (`f:deleted_at`, «ДД.ММ.ГГГГ ЧЧ:ММ»)
   - кнопка «Восстановить» (второстепенная, в строке справа)
6. Пагинация под таблицей: «Назад» / «Вперёд», «Показано 1–50 из N».

**Интерактив:**
1. **Смена вкладки**
   - **Элемент:** вкладка (Bootstrap `nav-tabs`), над таблицей
   - **UI:** вкладка подсвечивается сразу, таблица — индикатор загрузки; `kind` пишется в адресную строку, `offset` сбрасывается в 0, фильтры сохраняются
   - **Вызов:** `GET §6.3` → `/api/v1/deleted?kind={вид}&limit=50&offset=0` + текущие фильтры
   - **200:** `{ items, total, limit, offset }` → строки таблицы; счётчик пагинации под таблицей
   - **4xx (400 kind):** тост «Неизвестный вид записей»; **4xx (403):** тост «Нет доступа»
2. **Фильтры (поиск, период, кто удалил)**
   - **Элемент:** текстовый инпут, два поля даты, дропдаун — в панели фильтров
   - **UI:** поиск — debounce 300 мс; остальные — сразу при изменении; значения пишутся в адресную строку
   - **Вызов:** `GET §6.3` → `/api/v1/deleted?kind={вид}&q=…&deleted_from=…&deleted_to=…&deleted_by=…&limit=50&offset=0`
   - **200:** таблица перерисовывается; при `total` = 0 — «Ничего не найдено»
   - **4xx (400 q too_long):** красный текст под полем поиска «Строка поиска — не длиннее 100 символов»; **4xx (400 период):** красный текст под полями дат «Проверьте период»; **4xx (400 deleted_by):** тост «Проверьте фильтр «Кто удалил»»
3. **Сбросить**
   - **Элемент:** кнопка-ссылка, в панели фильтров справа
   - **UI:** четыре фильтра очищаются
   - **Вызов:** `GET §6.3` → `/api/v1/deleted?kind={вид}&limit=50&offset=0`
   - **200:** полный список вкладки
   - **4xx (403):** тост «Нет доступа»
4. **Восстановить**
   - **Элемент:** кнопка (второстепенная) в строке таблицы справа
   - **UI:** подтверждение `KT.uiDialog` «Восстановить «{title}»?» с кнопками «Восстановить» / «Отмена»; на время запроса кнопка заблокирована
   - **Вызов:** `POST §6.2` → `/api/v1/tasks/{id}/restore`
   - **200:** `{ id, warnings, notices }` → строка исчезает из таблицы, счётчик вкладки уменьшается; тост «Восстановлено»; при непустом `f:warnings` — жёлтый блок над таблицей: по строке на каждую пару товар × склад («Не хватает товара «Фильтр» на складе «Основной»: остаток −2») ; при `f:notices` с `column_replaced` — строка «Колонка заказа стала финальной — заказ поставлен в колонку «Новые»»; ссылка «Открыть заказ #128»
   - **4xx (409 NOT_DELETED):** тост «Запись уже восстановлена», строка исчезает
   - **4xx (404 TASK_NOT_FOUND):** тост «Заказ не найден», строка исчезает
   - **4xx (403):** тост «Нет доступа»
5. **Пагинация**
   - **Элемент:** кнопки «Назад» / «Вперёд» под таблицей слева
   - **UI:** `offset` пишется в адресную строку
   - **Вызов:** `GET §6.3` → `/api/v1/deleted?kind={вид}&limit=50&offset={N}` + текущие фильтры
   - **200:** следующая страница
   - **4xx (400 offset):** тост «Обновите страницу»

**Состояния:** потеря связи — тост «Нет связи с сервером», таблица остаётся прежней; перезагрузка страницы — вкладка, фильтры и страница восстанавливаются из адресной строки; запись восстановил другой администратор, пока экран открыт, — «Восстановить» вернёт 409 `NOT_DELETED`, строка исчезнет; новые удаления появляются при следующей загрузке списка (автообновления нет).

### §8.2. Экран/форма «Удаление» (общее окно с причиной)

**Как попадаем:**
- **Путь:** кнопка «Удалить заказ» в карточке заказа §8.3 (в частях 2–6 это же окно открывают остальные кнопки «Удалить»)
- **URL:** отдельного адреса нет — модальное окно поверх экрана
- **Роли:** admin (кнопки «Удалить» у исполнителя нет) · **Устройство:** десктоп, телефон
- **При открытии:** запросов нет
- **200:** — · **Пусто:** — · **4xx:** —

**Что на странице (сверху вниз):**
1. Заголовок «Удалить «{название записи}»?».
2. Пояснение (одна строка): «Товары заказа вернутся на склад. Заказ можно восстановить в разделе «Удалённые»». Текст пояснения — параметр окна: части 2–6 передают свой.
3. Форма:
   - Причина (`reason`) — textarea, 3 строки, обязательное, счётчик «0 / 500» под полем справа
4. Кнопки внизу справа: «Отмена» (второстепенная), «Удалить» (основная, красная).

**Интерактив:**
1. **Удалить**
   - **Элемент:** кнопка (основная, красная), внизу справа
   - **UI:** кнопка заблокирована на время запроса; пустая причина на клиенте не проверяется — проверяет сервер
   - **Вызов:** `DELETE §6.1` → `/api/v1/tasks/{id}`, body: `{ reason }`
   - **200:** `{ id, deleted_at, warnings }` → окно закрывается; карточка заказа закрывается, заказ исчезает с доски; тост «Удалено. Восстановить можно в разделе «Удалённые»»
   - **4xx (400 reason required):** красный текст под полем «Укажите причину удаления», окно остаётся
   - **4xx (400 reason too_long):** под полем «Причина — не длиннее 500 символов»
   - **4xx (400 reason invalid_text):** под полем «Недопустимые символы в причине»
   - **4xx (409 TASK_HAS_TRANSFERS):** текст ошибки красным блоком над кнопками «Сначала отмените перемещения: #N, #M», окно остаётся
   - **4xx (404 TASK_NOT_FOUND):** окно закрывается, тост «Заказ не найден», заказ исчезает с доски
   - **4xx (403):** тост «Нет доступа»
2. **Отмена**
   - **Элемент:** кнопка (второстепенная) внизу справа, крестик, Esc
   - **UI:** окно закрывается, введённая причина не сохраняется
   - **Вызов:** нет
   - **200:** —
   - **4xx:** —

**Состояния:** потеря связи — тост «Нет связи с сервером», окно остаётся с введённой причиной; запись удалил другой администратор — 404, окно закрывается.

### §8.3. Экран/форма «Доска и карточка заказа»

**Как попадаем:**
- **Путь:** главная страница (доска) → клик по карточке заказа
- **URL:** `/` и `/?task={номер}` (as-is)
- **Роли:** admin, executor · **Устройство:** десктоп, телефон
- **При открытии:** `GET /api/v1/tasks` и `GET /api/v1/tasks/:id/card` (as-is, §6.6)
- **200:** доска без удалённых заказов · **Пусто:** as-is · **4xx:** прямая ссылка на удалённый заказ — тост «Заказ не найден», карточка не открывается

**Что на странице (сверху вниз) — только изменения:**
1. Карточка заказа, кнопка «Удалить заказ» (admin, внизу слева, as-is расположение) — вместо нынешнего подтверждения открывает окно §8.2.

**Интерактив:**
1. **Удалить заказ**
   - **Элемент:** кнопка (второстепенная, красный текст), внизу карточки слева; только admin
   - **UI:** открывается окно §8.2
   - **Вызов:** `DELETE §6.1` → `/api/v1/tasks/{id}`, body: `{ reason }`
   - **200:** `{ id, deleted_at, warnings }` → карточка закрывается, заказ исчезает с доски; тост «Удалено. Восстановить можно в разделе «Удалённые»»
   - **4xx (400 reason):** под полем «Причина» в окне §8.2
   - **4xx (409 TASK_HAS_TRANSFERS):** в окне §8.2 «Сначала отмените перемещения: #N, #M»
   - **4xx (404 TASK_NOT_FOUND):** тост «Заказ не найден», карточка закрывается
   - **4xx (403):** тост «Нет доступа»
2. **Любая правка заказа, удалённого другим администратором, пока карточка открыта**
   - **Элемент:** любые кнопки и поля карточки
   - **UI:** as-is
   - **Вызов:** as-is адреса карточки (§6.6)
   - **200:** —
   - **4xx (404 TASK_NOT_FOUND):** ошибка в шапке карточки «Заказ не найден», после закрытия карточки заказ исчезает с доски

**Состояния:** заказ удалён, пока карточка открыта у другого пользователя, — следующее действие вернёт 404; доска обновляется при следующей загрузке (автообновления нет, as-is).
