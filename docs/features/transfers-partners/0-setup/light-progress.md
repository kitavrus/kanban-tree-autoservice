## Решения (одной строкой)
- Исполнитель: проверка скоупа — в сервисе (Head/Get → 404), роуты без RequireAdmin; создание чужого направления → 403 раньше валидации тела.
- PUT: сначала Head (404), потом валидация по направлению документа; direction/task_id в теле (*string/*int64 != nil) → not_allowed.
- client_id в теле POST/PUT принимается (strictJSON) и игнорируется.
- task_id <= 0 → `task_id: invalid`; заказ не найден → `not_found` (в т.ч. гонка с удалением: 23503 transfers_task_id_fkey).
- Единица в документе с клиентом: в task_equipment заказа И client_id единицы = клиент заказа, иначе not_in_task.
- Доп. индекс transfers_client_id_idx (FK RESTRICT, в спеке не перечислен).
- Down 0015: документы не-w2w удаляются, их единицы освобождаются (in_transit → at_client), причины supplier_in/client_out/transfer_unreceive → manual.
- Период: timezone.DayStart/NextDay (pkg/timezone), SQL: created_at >= from AND created_at < nextDay(to).
- transit_to_name для «склад → клиент» = строка «клиент».
- UI testids: st-new (dropdown toggle) + st-new-direction[data-direction]; st-filter-direction/supplier/task/from/to, st-filter-period-error; st-direction, st-task, st-task-info, st-task-error, st-task-link, st-supplier, st-supplier-error, st-task-equipment(-option/-location/-busy/-none), st-receive-now, st-qty-head, st-fact-head, st-row-direction/route/party, st-view-task/supplier; data-diff на st-view-received. Карточка: card-transfers, card-transfer-intake/-return (+-hint когда disabled), card-transfers-list, card-transfer-row/link/direction/warehouse/status/count/date, card-transfers-empty.
- Приёмка документов с клиентом — KT.uiDialog (ui-dialog-ok), тексты «Клиент получил оборудование?» / «Оборудование на складе?».
- «Принять сразу» — только у НОВОГО приёма от клиента (POST receive:true).
- Предвыбор из карточки (?new=1) включает и занятые единицы (сервер → 409 → в строке «уже в перемещении #N», TS-029 негатив); кнопки карточки активны, если есть единица at_client / at_warehouse.
- История единицы (clients/history.go): точка маршрута без склада = «клиент» (вне явных дельт спеки, иначе INNER JOIN терял документы с клиентом).
- TS-023 в E2E — экранная половина (момент TS-F5 приколот в ответах GET, даты периода уходят в запрос датами пользователя); граница суток в БД — Go live TestTS023_PeriodFilter_UserTimezone (момент создания в E2E задать нельзя, ADR-101).
- Fix-loop 1 (TR-015): некорректный период валидирует СЕРВЕР (§8.1 «400 (период): красный текст под полями периода», §6.1 `created_to: before_from`) — экран шлёт запрос и показывает «Некорректный период»; transfers.js не менялся. Причина падения — порядок шагов теста (сначала «по», потом «с» → промежуточный некорректный период до allowHttpErrors); исправлен порядок, 400 объявлены узко (точные created_from/created_to; task_id=abc), добавлена проверка «период исправлен → список перечитан, ошибка снята».
- Fix-loop 2 (ревью): checkRefs читает заказ `FOR KEY SHARE` (гонка DS-035/DS-026 со снятием единицы и сменой клиента; тест TestTS004_ParallelCreateVsTaskEquipmentChange); prefillFromTask не предвыбирает занятые единицы (негатив TS-029 в TR-012 — неактивная единица «в перемещении #N» + 409, когда единицу заняли при открытой форме); карточка: новое поле `equipment[].active_transfer_direction`, исполнителю «перемещение #N» ссылкой только у документов с клиентом (EW-002 — текст); TR-015 — период «вчера…завтра»; удалён неиспользуемый TaskEquipmentSendRequest.
- TS-032: в TR-014 помимо факта 12 (по спеке) добавлен второй приход с фактом 7 (недопоставка, data-loss).
- Ошибка удаления заказа 409 — как as-built: текст сервера в ошибке шапки карточки (showHeaderError), не тост.
