§1. Суть задачи

Удаление клиента и единицы оборудования становится восстановимым и больше не упирается в заказы и документы. Для администратора; исполнитель видит бейджи «удалён» в заказах и документах.

Бизнес (что делает пользователь/процесс):

  1. 1Администратор удаляет клиента с причиной — клиент и всё его оборудование уходят в «Удалённые»; заказы клиента остаются на доске (§8.1) — DS-014, DS-015.
  2. 2Администратор удаляет отдельную единицу оборудования с причиной (§8.1) — DS-014.
  3. 3Любой пользователь в заказе и в документе перемещения видит бейдж «удалён» у клиента и у единиц (§8.3) — DS-014.
  4. 4Администратор восстанавливает клиента — вместе с ним возвращаются единицы, ушедшие вместе с ним (§8.2) — DS-015.

Логика (правила системы):

  1. 5Клиент и единица удаляются при любых ссылках: отказы «У клиента есть заказы», «У оборудования есть перемещения», «Оборудование было в заказе» сняты — DS-014.
  2. 6Отказы — когда оборудование не у клиента: единица на нашем складе, в пути или в незавершённом документе не удаляется; клиент не удаляется, пока хотя бы одна его действующая единица на нашем складе, в пути или в незавершённом документе — сначала вернуть оборудование клиенту — DS-041, DS-014.
  3. 7Единица, ушедшая вместе с клиентом, получает причину клиента и пометку «вместе с клиентом»; отдельно восстановить её нельзя — сначала клиента — DS-015.
  4. 8Единицы, удалённые раньше клиента отдельно, при восстановлении клиента остаются удалёнными — DS-015.
  5. 9Удалённые клиент и единица не выбираются в новых заказах, услугах и строках документов; для обычных адресов не существуют (404) — DS-014, DS-026.
  6. 10Местоположение единицы при удалении и восстановлении не меняется — DS-008.
  7. 11Время: deleted_at — UTC (timestamptz), показ и фильтр — по поясу пользователя, «ДД.ММ.ГГГГ ЧЧ:ММ» — DS-025 (краткий дубль §3).
  8. 12Конкурентный доступ: удаляем клиента → одна транзакция «клиент + его единицы» под блокировкой строк единиц с проверкой «все у клиента и свободны»; удаляем единицу → условия «ещё не удалена», «у клиента», «не в незавершённом документе» в одном UPDATE; создаём заказ для клиента → проверка «клиент не удалён» под блокировкой строки клиента — DS-024 (краткий дубль §3).

Техника (API/данные/интеграции):

  1. 13Данные: три новые колонки в clients; четыре в equipment (плюс deleted_with_client); client_phones, tasks не меняются (§4).
  2. 14API: DELETE /api/v1/clients/:id и DELETE /api/v1/equipment/:id меняют поведение, запрос и ответ (§6.1, §6.3); новые POST /api/v1/clients/:id/restore, POST /api/v1/equipment/:id/restore (§6.2, §6.4); новые поля-признаки в ответах заказов и документов, условие «не удалён» в адресах клиентов и оборудования, виды clients, equipment в разделе «Удалённые» и служебной уборке (§6.5).
  3. 15Пакеты: internal/features/clients, internal/features/board, internal/features/transfers, internal/features/softdelete.
  4. 16Внешних систем нет.

UI (графическая часть):

  1. 17Справочник «Клиенты» и форма единицы оборудования: «Удалить» открывает общее окно с причиной (§8.1).
  2. 18«Удалённые»: новые вкладки «Клиенты» и «Оборудование» (§8.2).
  3. 19Доска, карточка заказа, «Перемещения»: бейджи «удалён»; удалённые не предлагаются в выборе (§8.3).

  4. 23Окончательное удаление — не делаем (решение пользователя, DS-012).

§3. Нефункциональные требования

Конкурентность (по операциям):

  1. 26Удаление клиента:
    • 27одна транзакция: строка клиента блокируется FOR UPDATE (нет либо удалён → 404 CLIENT_NOT_FOUND); действующие единицы клиента блокируются FOR NO KEY UPDATE по возрастанию id (as-is порядок блокировок документов); есть единица с location_status <> 'at_client' → 409 CLIENT_EQUIPMENT_AT_WAREHOUSE; есть единица с active_transfer_id IS NOT NULL → 409 CLIENT_EQUIPMENT_IN_TRANSFER; затем UPDATE клиента и всех его действующих единиц — те же три поля и deleted_with_client = true — DS-041, DS-015, DS-024
    • 28создание документа с единицей клиента одновременно с удалением клиента: занятие единицы ждёт блокировку строки equipment и проверяет deleted_at IS NULL — удаление выиграло → 400 equipment_id: not_found; документ выиграл → удаление клиента получает 409 CLIENT_EQUIPMENT_IN_TRANSFER — DS-041
    • 29единица, добавленная клиенту параллельно (исполнитель, POST /api/v1/clients/:id/equipment): создание читает клиента FOR KEY SHARE с условием deleted_at IS NULL — либо попадает в удаление вместе с клиентом, либо получает 404 CLIENT_NOT_FOUND — DS-015
  2. 30Восстановление клиента:
    • 31одна транзакция: UPDATE клиента с условием deleted_at IS NOT NULL (не удалён → 409 NOT_DELETED), затем очистка полей у его единиц с deleted_with_client = true — DS-015
  3. 32Удаление отдельной единицы:
    • 33один UPDATE с условиями deleted_at IS NULL, active_transfer_id IS NULL и location_status = 'at_client'; единица занята незавершённым документом → 409 EQUIPMENT_IN_TRANSFER; единица на нашем складе или в пути → 409 EQUIPMENT_AT_WAREHOUSE (DS-041); занятие единицы документом идёт под блокировкой строки equipment (as-is, FOR NO KEY UPDATE) и проверяет deleted_at IS NULL — гонка «удалить ↔ занять» даёт ровно один успех — DS-014
  4. 34Восстановление отдельной единицы:
    • 35один UPDATE с условием deleted_at IS NOT NULL; клиент единицы читается FOR KEY SHARE: удалён → 409 CLIENT_DELETED — DS-015
  5. 36Создание заказа и смена клиента заказа одновременно с удалением клиента:
    • 37проверка существования клиента (as-is tasks_repo.go:267) получает условие deleted_at IS NULL и блокировку FOR KEY SHARE: удаление выиграло → 400 client_id: not_found; создание выиграло → заказ остаётся у удалённого клиента с бейджем (допустимо, DS-014)
