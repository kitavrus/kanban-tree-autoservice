§1. Суть задачи

Удаление колонки доски становится восстановимым. Для администратора.

Бизнес (что делает пользователь/процесс):

  1. 1Администратор удаляет пустую колонку с причиной (§8.1) и возвращает её из «Удалённых» (§8.2) — DS-019, DS-020.
  2. 2Администратор восстанавливает заказ, колонку которого удалили: заказ появляется в первой нефинальной колонке, система сообщает об этом (§8.2) — DS-016.

Логика (правила системы):

  1. 3Удаляется только колонка без действующих заказов; удалённые заказы колонку не удерживают — DS-019.
  2. 4На доске всегда остаётся хотя бы одна действующая нефинальная колонка — DS-019.
  3. 5После удаления позиции оставшихся колонок идут подряд 1..N; восстановленная колонка встаёт в конец доски — DS-019.
  4. 6Заказ удалённой колонки при восстановлении ставится в конец первой нефинальной действующей колонки; товар списывается по правилу НОВОЙ колонки — DS-016, DS-039.
  5. 7Удалённая колонка не существует для обычных адресов: её нет в списке, в неё нельзя создать или перенести заказ, её нельзя править — DS-026.
  6. 8Время: deleted_at — UTC (timestamptz), показ и фильтр — по поясу пользователя, «ДД.ММ.ГГГГ ЧЧ:ММ» — DS-025 (краткий дубль §3).
  7. 9Конкурентный доступ: удаляем и восстанавливаем колонку → под блокировкой всех колонок, условие по deleted_at; переносим заказ в колонку → блокировка строки колонки с проверкой «не удалена» — DS-024 (краткий дубль §3).

Техника (API/данные/интеграции):

  1. 10Данные: три новые колонки в columns, CHECK и частичный индекс; tasks не меняется (§4).
  2. 11API: DELETE /api/v1/columns/:id меняет поведение, формат запроса и ответ (§6.1); новый POST /api/v1/columns/:id/restore (§6.2); дельта адресов колонок и заказов, вид columns в GET /api/v1/deleted и в служебной уборке (§6.3).
  3. 12Пакеты: internal/features/board (колонки, восстановление заказа), internal/features/softdelete (вид columns).
  4. 13Внешних систем нет.

UI (графическая часть):

  1. 14Доска, настройка колонки: «Удалить» открывает общее окно с причиной (§8.1).
  2. 15«Удалённые»: новая вкладка «Колонки»; предупреждение о замене колонки при восстановлении заказа (§8.2).

Out-of-scope:

  1. 16Перенос заказов из удаляемой колонки в другую автоматически — не делаем: непустая колонка не удаляется (as-is правило, DS-019).
  2. 17Восстановление заказа вместе с его удалённой колонкой одним действием — не делаем: пользователь выбрал «восстанавливать всегда с предупреждением» (решение пользователя, DS-016).
  3. 18Окончательное удаление — не делаем (решение пользователя, DS-012).

§3. Нефункциональные требования

Конкурентность (по операциям):

  1. 20Удаление колонки:
    • 21под блокировкой всех колонок (as-is ColumnRepo.LockAll, FOR UPDATE): проверки «нет действующих заказов» и «не последняя нефинальная» и сам UPDATE — в одной транзакции; колонка уже удалена → 404 COLUMN_NOT_FOUND — DS-019, DS-024
  2. 22Создание заказа в колонке и перенос заказа в колонку одновременно с её удалением:
    • 23перенос и создание читают колонку FOR SHARE (as-is tasks_repo.go:708) с условием deleted_at IS NULL; удаление ждёт эту блокировку и затем видит действующий заказ → 409 COLUMN_NOT_EMPTY; удаление выиграло → перенос получает 404 COLUMN_NOT_FOUND — DS-019
  3. 24Восстановление колонки:
    • 25под блокировкой всех колонок; UPDATE с условием deleted_at IS NOT NULL; позиция = максимум среди действующих + 1; не удалена → 409 NOT_DELETED — DS-019, DS-024
  4. 26Восстановление заказа удалённой колонки:
    • 27под блокировкой заказа (часть 1); новая колонка читается FOR SHARE — её параллельное удаление ждёт и получает 409 COLUMN_NOT_EMPTY — DS-016
  5. 28Правка и перестановка колонок (POST /api/v1/columns, PUT /api/v1/columns/:id):
    • 29перенумерация позиций (as-is Renumber, closeGaps) — только среди действующих колонок; удалённые хранят прежнюю позицию без смысла — DS-019

Аудит:

  • 30на колонке хранится последнее удаление: deleted_by, deleted_at, delete_reason; при восстановлении очищаются — DS-030

Время/таймзоны:
