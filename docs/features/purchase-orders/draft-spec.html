§1. Суть задачи

Закупка запчастей по дефициту: сотрудник (admin или executor) формирует список того, чего не хватает под принятые заказы и что ниже минимума, и отправляет его поставщику. Поставщик в своём кабинете отвечает, что соберёт и по какой цене. Мы забираем, список закрывается. Второй вариант — список «Базар (покупаем сами)» с печатью-чеклистом.

Состав:

Бизнес (что делает пользователь/процесс):

  1. 1Сотрудник открывает «Новый заказ», выбирает получателя (поставщик или «Базар»), видит строки дефицита с галочками и количеством, правит их, добавляет запчасти вручную, сохраняет черновик (§8.2, DS-002, DS-006).
  2. 2Сотрудник отправляет заказ поставщику. При необходимости правит отправленный заказ или отзывает его в черновик (§8.3, DS-012, DS-034).
  3. 3Поставщик входит под своим логином и видит заказы своего поставщика. По каждой строке ставит «Соберу, шт.», цену и комментарий, затем нажимает «Собрано, можно забирать» (§8.6–§8.7, DS-008).
  4. 4Сотрудник видит ответ: суммы, расхождения подсвечены. После того как забрали, нажимает «Забрали», и заказ закрывается. Остатки на складе этим НЕ меняются (§8.3, DS-010).
  5. 5Печать заказа в PDF (как акт выдачи): нам — с галочками для базара или с ценами после ответа, поставщику — свой экземпляр (§8.4, DS-014).
  6. 6Админ создаёт учётку поставщика на экране «Пользователи»: роль «Поставщик» + привязка к записи справочника suppliers (§8.5, DS-025, DS-044).

Логика (правила системы):

  1. 7Статусы: draft → sent → ready → picked_up; cancelled из draft/sent/ready. У «Базара» короткий путь draft → picked_up. У поставщика без активного входа возможен переход sent → picked_up (§5, DS-011, DS-042).
  2. 8Количество «к заказу» по запчасти = max(0, pending + min_stock − stock). Признак строки for_orders, если pending > stock, иначе below_min (§6.10, DS-003).
  3. 9Подсказка «уже в открытом заказе З-0012 — 5 шт.» учитывает только заказы в sent и ready. Галочка у такой строки по умолчанию снята, количество предлагается без вычета (DS-004, DS-049).
  4. 10Правка строки в sent (количество или запчасть, добавление строки) сбрасывает ответ поставщика по ЭТОЙ строке и ставит у неё пометку «Изменено заказчиком». Правка примечания заказа ответы не сбрасывает: у поставщика заказ помечается «Изменён», новое примечание подсвечивается (DS-034, DS-048).
  5. 11После ready строки только для чтения. Поставщик не может отменить своё «Собрано» (DS-038, DS-039).
  6. 12Executor видит в списке, открывает, печатает и меняет ТОЛЬКО свои заказы (created_by = он); чужой id → 404, как у поставщика. Admin видит все заказы и делает с ними всё. Удаление, восстановление и окончательное удаление черновика доступны только admin (DS-050, DS-051, DS-060).
  7. 13Подсказка «уже в открытом заказе» на экране «Новый заказ»: у admin учитывает все открытые заказы (sent/ready), у executor — только его собственные. Номера чужих заказов исполнителю не показываются (DS-078).
  8. 14Время: храним в UTC (timestamptz), показываем в поясе смотрящего (timezone пользователя, по умолчанию Asia/Almaty). Фильтров по дате нет (DS-033).
  9. 15Конкурентный доступ по операциям:
    • 16правка черновика или отправленного заказа и все переходы статусов — оптимистичная блокировка по version заказа, устаревшая версия → 409;
    • 17ответ поставщика по строке — своя version строки, второй сохраняющий → 409;
    • 18«Собрано» и «Отозвать» одновременно — выигрывает первый, второй получает 409 (DS-032).

Техника (API/данные/интеграции):

  1. 19Новые таблицы purchase_orders и purchase_order_items (строки, ON DELETE CASCADE). В users добавляются роль supplier и supplier_id (§4).
  2. 20API закупок для нас (§6.1–§6.11) и API кабинета поставщика (§6.12–§6.16) по CLAUDE.md §API-1. Учётки поставщиков — через расширение API users (§6.17).
  3. 21Безопасность: правило «по умолчанию запрещено» для роли supplier в RequireAPI/RequireSSR. Поставщику открыты только /supplier/*, /api/v1/supplier/*, выход и смена своего пояса (DS-017, DS-053).
  4. 22Расчёт дефицита переиспользует CTE pending из internal/features/board/stock_repo.go. Страница /stock не меняется (DS-005, DS-064).
  5. 23Черновик — новый вид «Закупки» в разделе «Удалённые» (internal/features/softdelete) (DS-037, DS-072).

UI (графическая часть):

  1. 24Сайдбар сотрудника → пункт «Закупки» (обе роли) → список /purchases с фильтром по статусу (§8.1).
  2. 25«Новый заказ» /purchases/new: выбор получателя → таблица дефицита с галочками и количеством → поиск «Добавить запчасть» → «Сохранить черновик» (§8.2).
  3. 26Карточка /purchases/:id: строки, колонки ответа поставщика, кнопки по статусу («Отправить поставщику», «Сохранить», «Отозвать», «Забрали», «Отменить», «Удалить», «Печать») (§8.3).
  4. 27PDF-форма заказа (§8.4).
  5. 28«Пользователи»: в форме роль «Поставщик» + выпадающий список поставщиков (§8.5).
  6. 29Кабинет поставщика, удобный с телефона: свой упрощённый сайдбар, список /supplier/orders, карточка /supplier/orders/:id с полями по строкам и кнопкой «Собрано, можно забирать» (§8.6–§8.7).

Out-of-scope:

  2. 31Изменения страницы «Остатки» /stock (отметка «заказано» и т.п.): решено не трогать (DS-005).
  3. 32Уведомления поставщику и нам (Telegram, ссылка в WhatsApp): позже (DS-028).
  4. 33Кнопка «Дозаказать недостающее» в карточке заказа клиента: позже (DS-028).
  5. 34Основной поставщик у запчасти и история закупочных цен: позже, связи «запчасть ↔ поставщик» нет (DS-028).
  6. 35Отдельный журнал изменений «было → стало»: решено не вести, хватает полей «кто/когда» (DS-052).

§3. Нефункциональные требования

Конкурентность (по операциям, DS-032):

  1. 41Правка заказа (§6.4) и переходы статусов (§6.6–§6.9):
    • 42механизм: UPDATE … WHERE id = :id AND version = :version AND status IN (…), затем version + 1;
    • 43конкурент: устаревшая версия → 409 PURCHASE_ORDER_VERSION_CONFLICT «Заказ изменился, обновите страницу».
  2. 44Ответ поставщика по строке (§6.14):
    • 45механизм: version строки + guard по статусу заказа sent в одной транзакции;
    • 46конкурент: устаревшая версия строки → 409 PURCHASE_ITEM_VERSION_CONFLICT; заказ уже не sent → 409 PURCHASE_ORDER_READ_ONLY.
  3. 47«Собрано» (§6.15) против «Отозвать»/«Отменить»/правки (§6.7, §6.9, §6.4):
    • 48механизм: атомарный guard WHERE status = 'sent';
    • 49конкурент: выигрывает первый, второй → 409, экран перечитывается.
  4. 50Правка строки в sent против одновременного ответа поставщика по той же строке:
    • 51механизм: сброс ответа и пометка «Изменено заказчиком» увеличивают version строки;
    • 52конкурент: поставщик со старой версией → 409, видит новую строку без ответа (DS-048).
  5. 53Номер заказа: выдаёт sequence purchase_orders_number_seq, без гонок и без переиспользования (DS-015).

Аудит (DS-052):

  • 54у заказа: created_by/created_at, sent_by/sent_at, ready_by/ready_at, picked_up_by/picked_up_at, cancelled_by/cancelled_at/cancel_reason, deleted_by/deleted_at/delete_reason;
  • 55у строки: supplier_answered_by/supplier_answered_at — кто из учёток поставщика ответил последним;
  • 56отдельного журнала «было → стало» нет; аудит чтения и печати не ведём.

Время/таймзоны (DS-033):

  • 57хранение — UTC, все отметки времени timestamptz;
  • 58показ в списке, карточке, PDF и кабинете — в поясе смотрящего (timezone, по умолчанию Asia/Almaty; поставщик может сменить, PUT /api/v1/users/me/timezone ему разрешён);
  • 59фильтров и отчётов по диапазонам дат нет;
  • 60источник времени — now() БД; порядок — number (sequence).

Метрики/таймстемпы:

  • 61sent_at → ready_at → picked_up_at дают длительность «отправили → собрано → забрали»; отчётов и алертов в MVP нет (inferred, DS-052).

Offline / деградация / восстановление:

  • 62SSR, всё состояние на сервере. После перезагрузки страница перечитывает заказ. Несохранённый ввод в полях поставщика теряется: каждая строка сохраняется отдельно по кнопке или blur (§8.7, inferred DS-063).

Логирование и чувствительные данные:

  • 63slog с trace_id (as-is каркас); цены поставщика и комментарии в логи не пишем;
  • 64поставщик не видит reason строки, наши продажные цены (products.price), отменённые заказы и причины отмены (DS-041, DS-046).

Формат ошибок:

  • 65pkg/errorspkg: { "code", "message", "details" }; 400 → details.fields[] (проектный CLAUDE.md); 403 / 404 / 409 — по смыслу (§6).

Abuse cases (вход для adversarial E2E TD-4):

  1. 66Поставщик открывает существующие разделы (/, /stock, /clients, /catalog/*, /suppliers, /users, /calendar, /executor-payouts, /deleted, /tasks/:id/print/* и все /api/v1/* кроме своих) → SSR: редирект на /supplier/orders, API: 403 (DS-017, DS-053). Смягчение — правило «по умолчанию запрещено» в middleware + live-тест на каждый раздел.
  2. 67Поставщик подставляет чужой id заказа или строки → 404 (DS-017).
  3. 68Поставщик передаёт в body supplier_id/order_id → игнорируется, поставщик берётся из сессии (DS-053).
  4. 69Executor открывает, печатает, правит или отменяет чужой заказ по id → 404 PURCHASE_ORDER_NOT_FOUND, как будто заказа нет; в списке чужих нет (DS-051, DS-060). Подсказка §6.10 у executor считает только его заказы — номера чужих не раскрываются (DS-078).
  5. 70Executor пытается удалить черновик или выдать учётке роль supplier → 403 (DS-050, DS-044).
  6. 71Дубли закупок: два исполнителя независимо заказывают одну запчасть — подсказка §6.10 у каждого видит только свои заказы. Риск принят пользователем (DS-078); admin видит все открытые заказы и может снять дубль отменой.

Применённые zap-дефолты (zap-list — стандарты проекта из CLAUDE.md, применяются автоматически, без вопросов; в §9 источник zap):

  • 72формат ошибок — pkg/errorspkg, 400 details.fields[] (DS-065);
  • 73коды not found / forbidden / conflict → 404 / 403 / 409 (DS-065);
  • 74синхронная обработка, без очередей (DS-065);
  • 75миграции не применяются автоматически, только make migrate-up (DS-065).
