# Kanban-tree — план

## 1. Стек (по образцу zerem_wms)
- **Backend:** Go 1.26+, Fiber v3, pgx/v5, golang-migrate (`migrations/`, раннер `cmd/migrate`), go-redis v9.
- **Frontend:** Go `html/template` (SSR: общий layout `web/ssr/_layout/templates` (вне корня статики `web/ssr/_shared`), страницы фич — `web/ssr/{feature}/templates`, рендерер `internal/ssr`) + чистый JS (без фреймворков и без сборки). **Основа стилей — vendored Bootstrap 5.3** (как zerem_wms и `/z-scaffold`, D38); вид прототипа — через `--bs-*`-токены и `web/ssr/_shared/app.css` (primary `#2563EB`), тёмная тема — `data-bs-theme`. Общие JS: `theme.js`, `api.js` (fetch + CSRF), `ui-dialog.js` (диалоги на Bootstrap Modal), `combobox.js` (поиск в любом `select.form-select`). Доска и модалки — vanilla JS поверх JSON API.
- **Drag & drop:** нативный HTML5 DnD (без библиотек); позиция карточки — дробный `position` (меняется одна строка при переносе).
- **Файлы:** локальный диск (volume `uploads`), интерфейс `FileStore` → позже MinIO/S3 без переписывания. Превью для фото, `<video>` для видео, ссылка для PDF. Лимиты: фото 20 МБ, видео 500 МБ, PDF 20 МБ (D21).
- **Инфра:** docker-compose (`postgres:18`, `redis:8` — из каркаса). Makefile: `fresh-start` (первый запуск), `local-up[-seed]` / `local-down` / `local-reset`, `run`, `migrate-up/down`, `test`, `test-integration[-scoped]`, `lint`, `e2e-install` / `e2e` / `e2e-full`; seed-админ — `cmd/seed` (`admin`/`admin1234`), `seed-demo` (демо-данные прототипа, только локально — D36, фаза 5). Имён с `dev` нет намеренно — зарезервированы под удалённый dev-контур `/infra-bootstrap`.
- **E2E:** `e2e/` (Playwright, только chromium headed, `--workers=1`), POM `e2e/pages`, фикстура чистоты консоли/сети `e2e/fixtures/test.ts`.
- **Каркас:** `/project-bootstrap` (`auth.mode=session`, `components.frontend=false`); справочники — `/z-scaffold` (SSR), доска / карточка заказа / «Остатки» — вручную поверх JSON API (D30).
- **Режимы:** CM-1 = **MVP**; US-1 = `swagger:no / adaptive:min / themes:both` (D31).

## 2. Авторизация (стандартная сессия, как в zerem_wms)
- `GET/POST /login`, `POST /logout`; bcrypt; сессия в Redis `session:<sid>`, sliding TTL 12 ч + абсолютный максимум 7 дней; параллельные сессии с разных устройств разрешены (D35).
- Cookie `sid` HttpOnly, SameSite=Strict, `Secure` по `SESSION_COOKIE_SECURE`; CSRF double-submit без хранилища (cookie `kt_csrf` ↔ `_csrf` в формах / `X-Csrf-Token` в fetch, плюс проверка `Origin`; D40) — на всех мутациях, включая `/api/v1` и `/login`.
- Защита от перебора: `LOGIN_MAX_FAILURES` неудачных входов по логину за `LOGIN_FAILURE_WINDOW` → 429 (D41). Ответ для «нет логина» и «неверный пароль» одинаковый; о блокировке сообщается только при верном пароле.
- Middleware: SSR-гард → редирект на `/login?redirect=…` (только локальные пути), API-гард → 401; admin-гард → 403 (API — JSON, страницы — «Нет доступа»). Роль и активность читаются из БД на каждом запросе — смена роли действует без перелогина; блокировка убивает все сессии, смена пароля — все, кроме текущей своей (D42).
- Пользователи: таблица `users` (login, password_hash, name, role `admin|executor`, phone, active). Первый админ — через `make seed`.
- **Роли:**
  - `admin` — всё: справочники (клиенты, услуги), сотрудники, колонки, оплата, удаление заказов, правка остатков.
  - `executor` (D19) — вся доска, по умолчанию фильтр «мои» (ответственный по заказу или исполнитель хотя бы одной услуги), фильтр снимается; создание/редактирование заказов (включая цены работ и товаров в заказе), новое оборудование клиента, статусы услуг, журнал, вложения; «Остатки» — только просмотр. Удалять заказы нельзя. Меню справочников не видит, API справочников на запись → 403 (кроме создания оборудования из карточки заказа).
- Нельзя заблокировать себя; нельзя заблокировать / снять роль admin у последнего активного администратора → 409 (D29).

## 3. Модель данных
Дерево: **Заказ (задача)** → **Услуги (подзадачи)** → **Товары** внутри услуги.
```
users(id, login, password_hash, name, role ENUM(admin|executor), phone, active, created_at)

clients(id, company_name, address, contact_name, contact_position, created_at, updated_at, version)
client_phones(id, client_id → clients, phone, note)                 -- 1..N телефонов

-- оборудование клиента (то, что привозят в ремонт)
equipment_types(id, name, spec_keys TEXT[], is_active)              -- «Лазерный источник»: Мощность, Длина волны…
equipment(id, client_id, type_id, brand, model, sku, serial, specs JSONB [{k,v}], note)  -- DELETE только если ни разу не было в заказе (D26)
task_equipment(task_id, equipment_id, completeness, condition)      -- принято по заказу: комплектность, состояние

-- каталог
catalog_categories(id, kind ENUM(service|product), name, position, is_active)  -- UNIQUE(kind, lower(btrim(name)))  -- «Ремонт», «Замена узлов» | «Фильтры», «Запчасти»
products(id, category_id, name, sku, unit, price NUMERIC(12,2), is_active,
         stock NUMERIC(12,3) DEFAULT 0, min_stock NUMERIC(12,3) DEFAULT 0,
         box TEXT, place TEXT)   -- остаток (может уйти в минус), минимум, коробка, место (стеллаж/полка)
services(id, category_id, name, price NUMERIC(12,2) NULL, is_active)          -- NULL = «по факту»
service_products(service_id, product_id, qty NUMERIC(12,3))         -- типовой комплект товаров услуги

-- доска
columns(id, name, color, is_final, consumes_stock BOOL, position)   -- колонка = статус заказа; consumes_stock — товары заказа списаны
tasks(id BIGSERIAL /* номер заказа #id, сквозной — D37 */, column_id, client_id NOT NULL, title, description_html,
      assignee_id → users NULL, due_date NULL, is_paid BOOL, paid_at NULL,
      position NUMERIC, created_by, created_at, updated_at, version)
subtasks(id, task_id, service_id → services, status ENUM(new|in_progress|done),
         assignee_id NULL, due_date NULL, price NUMERIC(12,2) NULL,
         equipment_id → equipment NULL, position)  -- подзадача = услуга; equipment_id — к какой принятой единице относится
subtask_products(id, subtask_id, product_id, qty NUMERIC(12,3), price NUMERIC(12,2))  -- товары в услуге заказа; дробное кол-во (м, л) — D33
task_stock(task_id, product_id, qty NUMERIC(12,3))                  -- сколько уже списано по заказу (аналог writtenOff прототипа)
stock_movements(id, product_id, task_id NULL, qty_delta NUMERIC(12,3), reason ENUM(task_consume|task_return|manual), user_id, created_at)  -- журнал движения остатков
subtask_logs(id, subtask_id, user_id, text, created_at, updated_at)         -- журнал работ по услуге (многодневные работы)
attachments(id, task_id, kind(photo|video|file), orig_name, mime, size, storage_key, created_by, created_at)  -- file = PDF
```
- **Статус заказа = колонка.** Перенос карточки меняет статус; цвет карточки — цвет колонки. Колонка с `is_final` = заказ выполнен (не подсвечивается как просроченный). Колонки и их цвет настраивает админ.
- **Статус услуги** (new / in_progress / done) меняется вручную.
- **Финальная колонка:** перенос заказа в `is_final`-колонку запрещён, пока не все услуги в статусе done (сервер → 409 `SUBTASKS_NOT_DONE` со списком; UI — сообщение). Проверка и на `move`, и на `PUT` задачи со сменой колонки. Пока заказ в финальной колонке — нельзя вернуть услугу из done и нельзя добавить новую услугу (409) (D22).
- **Колонки (D23):** удалить колонку с заказами → 409; финальных может быть несколько, но минимум одна колонка нефинальная (409). Смена `consumes_stock` у колонки → пересчёт списания всех её заказов в одной транзакции. Сид колонок (D32): «Новые», «Согласование» — без списания; «В работе», «Ждёт запчасти» — списывают; «Готово» — финальная, списывает.
- **Журнал работ услуги:** записи «что сделано / что осталось» с автором и временем; правка (`PUT`) и удаление — своя запись, админ — любая (D27). Последняя запись видна на карточке доски.
- **Удаление справочников (D26):** неиспользуемое → DELETE; используемое (услуга, товар, категория, тип оборудования) → 409, вместо удаления — архив `is_active=false` (скрыто из выбора, старые заказы не трогаются). Клиент с заказами → 409. Оборудование — DELETE, только если ни разу не было в заказе, иначе 409.
- **Конкурентность склада (D34):** перенос заказа, смена колонки и правка товаров заказа пересчитывают `task_stock` и `products.stock` в одной транзакции с `SELECT … FOR UPDATE` по строкам товаров (в порядке id — без дедлоков); каждая дельта → `stock_movements`. Ручная правка остатка (admin) → `manual` с дельтой.
- **Печать актов (D20):** HTML-страницы `/tasks/:id/print?kind=intake|handover` (акт приёма / выдачи: клиент, оборудование, комплектность, состояние; для выдачи — услуги, товары, итог), печать/PDF средствами браузера.
- **Оборудование клиента:** реестр единиц у клиента (тип, производитель, модель, артикул, серийный №/VIN, характеристики по шаблону типа). В заказ добавляется из реестра клиента или заводится новое; комплектность и состояние фиксируются на уровне заказа. Повторный ремонт той же единицы → видна история заказов. Поиск на доске — по модели/SN.
- **Товары** — для расчёта стоимости + простой учёт наличия: количество в наличии, минимальный остаток, коробка и место хранения (стеллаж/полка).
- **Списание (D17):** товары заказа списываются, когда заказ попадает в колонку с `consumes_stock` (по умолчанию «В работе» и все дальше, включая финальную) — заказ согласован с клиентом. Уже списанное по заказу хранится; при правке товаров в заказе дописывается/возвращается разница, при возврате заказа в колонку без списания или удалении заказа — товары возвращаются на склад. Остаток может уйти в минус (долг) — не блокирует, но предупреждает.
- **Минимальный остаток (D18):** после списания, если товар ≤ минимума, — предупреждение с перечнем (и ссылкой на экран «Остатки»); в карточке заказа у каждого товара подсказка «в наличии / останется / не хватает». Экран **«Остатки»** (виден всем, правка — admin): KPI (на минимуме / нет в наличии / уйдут в минимум после заказов), таблица рисковых товаров с прогнозом с учётом ещё не взятых в работу заказов; счётчик в меню.
- **Оплата:** `is_paid` (Оплачен / Не оплачен), меняет только админ; метка на карточке, фильтр на доске.
- **Цены:** при добавлении услуги в заказ копируются цена работы и комплект товаров с текущими ценами (`subtasks.price`, `subtask_products.price`) — правятся в заказе, изменения прайса старые заказы не трогают. Цена и срок услуги необязательны.
- **Итог заказа** = Σ цен работ + Σ (qty × price) товаров; на карточке и в колонке.
- **Срок:** у заказа и у каждой услуги (необязательно). Просрочен — красный, сегодня/завтра — оранжевый.
- Оптимистичная блокировка `version` у клиентов и заказов (два пользователя правят одну карточку → 409); услуги и товары в заказе — last-write-wins (D28).
- Описание — HTML из простого редактора; на сервере — санитайзер (bluemonday).

## 4. API (JSON, snake_case, списки `{items,total,limit,offset}`)

|---|---|
| Клиенты | `GET/POST /api/v1/clients`, `GET/PUT/DELETE /api/v1/clients/:id` (телефоны — массив внутри) |
| Каталог | `GET/POST/PUT /api/v1/catalog-categories?kind=`, `GET/POST/PUT/DELETE /api/v1/services` (с комплектом `products[]`), `GET/POST/PUT/DELETE /api/v1/products` |
| Доска | `GET /api/v1/board?client_id=&q=&category_id=&is_paid=&assignee_id=&due=overdue\|soon` → колонки + карточки |
| Сотрудники (admin) | `GET/POST /api/v1/users` (`?q=&role=&is_active=&sort=&order=&limit=&offset=`), `GET/PUT /api/v1/users/:id` (PUT — полная карточка, пароль пустой = не менять; блокировка = `is_active:false`, сессии убиваются; удаления нет — D39). Ошибки: `LOGIN_TAKEN` 409, `SELF_BLOCK` 409, `LAST_ADMIN` 409. SSR: `/users`, `/users/new`, `/users/:id` |
| Вход | `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, `GET /api/v1/auth/me`; SSR: `GET/POST /login`, `POST /logout` |
| Колонки (admin) | `POST/PUT/DELETE /api/v1/columns` (name, color, is_final), `POST /api/v1/columns/:id/move` |
| Задачи | `POST/GET/PUT/DELETE /api/v1/tasks/:id`, `POST /api/v1/tasks/:id/move {column_id, before_id, after_id}` |
| Услуги заказа | `POST /api/v1/tasks/:id/subtasks {service_id}` (копирует комплект), `PUT/DELETE /api/v1/subtasks/:id` |
| Журнал услуги | `GET/POST /api/v1/subtasks/:id/logs`, `PUT/DELETE /api/v1/subtask-logs/:id` (автор или admin) |
| Оборудование | `GET/POST /api/v1/clients/:id/equipment`, `GET/PUT/DELETE /api/v1/equipment/:id`, `GET/POST/PUT/DELETE /api/v1/equipment-types` |
| Остатки | `GET /api/v1/stock` (KPI + товары с прогнозом), `PUT /api/v1/products/:id` с `stock` (admin → `manual`) |

## 5. Экраны
1. **Логин.**
2. **Доска заказов** — фильтры: клиент, поиск (заказ/описание/услуга/товар/#номер), вид работ, оплата, исполнитель, срок. Колонки = статусы (цвет, сумма по колонке), drag&drop карточек. Карточка в цвете колонки: название, клиент, оплачен/не оплачен, чипы услуг, прогресс услуг, просроченные услуги, вложения, срок, сумма, ответственный.
3. **Карточка заказа** — принятое оборудование (комплектность, состояние, история ремонтов), название, клиент, статус (колонка), ответственный, срок, оплата, описание, фото/видео, итоги (работы/товары/всего); блок **«Услуги»**: каждая — статус, исполнитель, срок, цена + таблица товаров (кол-во × цена), добавление услуги из каталога подставляет комплект.
4. **Клиенты** — таблица + форма: компания, адрес, представитель (ФИО, должность), телефоны, оборудование клиента (с числом заказов по каждой единице).
5. **Каталог** — вкладки «Услуги» / «Товары» / «Типы оборудования», категории слева; у услуги — цена (или «по факту») и комплект товаров.
6. **Сотрудники** (admin) — список, создание, роль, пароль, блокировка.
- **Все выпадающие списки — с поиском** (`combobox.js` поверх нативного `<select>`).

## 7. Решения
- D1. Подзадачи — только внутри карточки заказа; подзадача = услуга из каталога.
- D2. Доска одна.
- D3. Цены: прайс в каталоге → копия в заказе, правится; у услуги цена необязательна.
- D4. Роли: администратор и исполнители; исполнитель назначается на заказ и на услугу.
- D5. Срок — у заказа и (необязательно) у услуги.
- D6. Все выпадающие списки — с поиском.

- D45. Склады (`docs/features/warehouses/draft-spec.md`, подфаза A): справочник `warehouses` (admin, без удаления, уникальность имени вкл. архивные → 400 `fields[name]`), остатки — по паре товар×склад в `product_stock` (`products.stock/min_stock/box/place` удалены миграцией 0008, всё перенесено на «Алматы»); `subtask_products`/`task_stock`/`stock_movements` несут `warehouse_id`, StockEngine.Reconcile работает по паре (смена склада строки = возврат + списание). **Пересматривает D34 в части ключа блокировки** (`product_stock` FOR UPDATE по (product_id, warehouse_id)). *(warehouses A)*
- D46. API товара: вместо `stock/min_stock/box/place` — `stocks[]` (строки складов, частичная правка: неуказанные склады не меняются) + `total_stock`; `PUT /api/v1/stock/:id` требует `warehouse_id`. `/api/v1/warehouses` — целиком admin; склады для select'ов приходят в ответах карточки заказа/«Остатков». *(warehouses A)*
- D47. Последний активный склад архивировать нельзя (409 `WAREHOUSE_LAST_ACTIVE`). *(warehouses A)*
- D48. «Учитываемая» пара товар×склад = есть строка `product_stock` либо потребность заказов; пустые пары (0/0 без строки) не попадают в риск/KPI/бейдж и не создаются формой товара; новый товар всегда получает строку склада по умолчанию. *(warehouses A)*
- D49. Склад по умолчанию — первый активный по position (`default_warehouse_id()`, он же DEFAULT колонок `subtask_products/stock_movements.warehouse_id`); склад оборудования услуги как умолчание (DS-005) включится в подфазе C вместе с `task_equipment.warehouse_id`. *(warehouses A)*
- D50. Перемещения товаров (подфаза B, DS-006/DS-007): отдельный пакет `internal/features/stocktransfers`, не board — StockEngine завязан на заказ; блокировка остатков переиспользует механику D34/DS-005 в виде set-based SQL (ensure `INSERT … ON CONFLICT DO NOTHING` → `FOR UPDATE` строк `product_stock` в порядке (product_id, warehouse_id)), Lock Order: строка `stock_transfers` FOR UPDATE → `product_stock`. «В пути» на «Остатках» = сумма `qty_sent` строк перемещений `in_transit` по товару; при фильтре склада — только входящие в этот склад (CTE `transit` в `board/stock_repo.go`).
- D51. API `/api/v1/stock-transfers`: `POST` (`send: true` — сразу in_transit), `PUT /:id` — только `requested` (строки целиком), `POST /:id/send|receive|cancel` с обязательным `version`; version сверяется ДО статуса (устаревшая форма → 409 `STOCK_TRANSFER_VERSION_CONFLICT`, недопустимый переход/финальный статус → 409 `STOCK_TRANSFER_STATUS_CONFLICT`); id — bigserial (#N), битый/чужой id → 404. Список — `{items,total,limit,offset}` (limit по умолчанию 50, max 500), фильтры `status`, `warehouse_id` (откуда ИЛИ куда). **Пересмотрено D73/D77 (2026-10-07, transfers, часть 6):** «Получено» больше не финальный статус — администратор возвращает документ в «В пути» действием «Отменить проведение» с обязательной причиной (DS-017); документ в «Заявка» / «Отменён» удаляется (только admin).
- D52. Строки перемещения: дубль товара — 400 `items[i].product_id: duplicate` (не слияние, в отличие от комплекта услуги D10); `qty_sent` > 0, NUMERIC(12,3); не более 200 строк; склады — активные, from ≠ to (400 `to_warehouse_id: same_warehouse`, плюс CHECK в БД); архивный товар, уже бывший в заявке, допустим при пересохранении.
- D53. Приёмка: строка без записи в `items` — факт = `qty_sent`; `0 ≤ qty_received ≤ qty_sent` (400 `exceeds_sent`). Журнал на получателе: `transfer_in +qty_sent` и при недостаче `transfer_loss −(qty_sent−qty_received)`, остаток получателя растёт на факт. Отправка в минус разрешена — ответ несёт `warnings[]` по источнику (negative/below_min, как D17/D18). Отмена `in_transit` → `transfer_return +qty_sent` на источник; отмена `requested` — без движений.
- D54. Экран «Перемещения» (admin, пункт «Работа → Перемещения»): master-detail на JS поверх API (как «Остатки»), выбранное перемещение — `?id=N`; «Отправить» у существующей заявки сначала сохраняет правки (PUT), затем отправляет; отмена — модальный `KT.uiDialog`, приёмка — модалка с фактом по строкам. Журнал движений в UI нигде не выводится — ссылки «на перемещение из журнала» нет (`stock_movements.transfer_id` с FK ON DELETE SET NULL готов для будущего экрана).
- D55. Склад оборудования заказа (warehouses подфаза C, DS-008, миграция 0010): `task_equipment.warehouse_id` (текущий склад, NULL только в пути, DEFAULT `default_warehouse_id()` для служебных вставок) + `status ∈ at_warehouse|in_transit` + маршрут `transit_from_warehouse_id`/`transit_to_warehouse_id` — исходный склад храним ОТДЕЛЬНОЙ колонкой (warehouse_id в пути обнулён по спеке), согласованность — CHECK `task_equipment_location_check`. Существующие строки → «Алматы». Журнал `task_equipment_movements` (bigserial; task/equipment ON DELETE CASCADE, переживает удаление единицы из заказа; `user_id` NOT NULL RESTRICT, ADR-007).
- D56. `POST /tasks/:id/equipment` — `warehouse_id` опционален в API (пусто → первый активный склад, как строка товара D49), в UI select «Склад приёма» всегда заполнен; несуществующий/архивный → 400 по полю. Запись `received` — только при реальной вставке (повторный идемпотентный POST журнал не пишет).
- D57. Переходы `POST /tasks/:id/equipment/:equipment_id/send {to_warehouse_id}|receive|cancel-transit` (права как у правки оборудования, D19 — и executor): LockTask → `SELECT … FOR UPDATE` строки task_equipment. Уже в пути → 409 `TASK_EQUIPMENT_IN_TRANSIT`; приём/отмена не в пути (в т.ч. повторный приём) → 409 `TASK_EQUIPMENT_NOT_IN_TRANSIT`; на тот же склад → 400 `to_warehouse_id: same_warehouse`; архивный/несуществующий склад → 400. Журнал: `sent` from→to, `arrived` from→to, `cancelled` хранит отменённый маршрут from→to (возврат на from). Ответ — карточка (re-fetch). Удаление единицы в пути не запрещено (как раньше).
- D58. Склад по умолчанию строки товара (DS-005, закрывает TS-006): склад оборудования услуги (`subtasks.equipment_id` → task_equipment заказа), если единица at_warehouse и склад активен; иначе первый активный. Существующие строки при смене оборудования/перемещении не пересчитываются.
- D59. Доска: `GET /tasks?warehouse_id=` — заказы с оборудованием at_warehouse на X или in_transit с назначением X; `has_in_transit` в элементах списка и в `GET /tasks/:id` (бейдж «🚚 в пути»). Опции фильтра «Склад» рендерит SSR доски (все склады, архивные с пометкой) — `/api/v1/warehouses` только admin, а фильтр нужен и executor. Ленивая загрузка колонок (`per_column`/«Показать ещё») получает фильтр тем же tasksQuery. История оборудования (`/equipment/:id/history` и панель в карточке) показывает склад единицы в каждом заказе (`equipment_status`, `location`).
- D60. seed-demo (DS-012): товары с остатком ≥20 — ¼ на «Москве»; перемещения Алматы → Москва: одно received, одно in_transit (движения transfer_out/transfer_in, остатки правятся теми же дельтами); оборудование трёх заказов (без списаний с дефицитом) — на «Москве», их товары — тоже с «Москвы»; одна единица в пути Алматы → Москва; у каждой единицы журнал `received`. Guard «заказы есть → no-op» не менялся.
- D61. Оборудование заказа в пути (in_transit) убрать из заказа нельзя: DELETE → 409 `TASK_EQUIPMENT_IN_TRANSIT`, кнопки «Убрать» у такой единицы нет; сначала «Принять» или «Отменить отправку». D58 (строки товаров не следуют за переездом оборудования) подтверждено пользователем 2026-10-02.
- D62. Выплаты исполнителям (executor-payouts, решения пользователя 2026-10-05): статус «выплачено ли исполнителю за услугу» ведётся на уровне услуги заказа (`subtasks`), флаг на каждой услуге. Менять флаг и сумму выплаты вправе И администратор, И исполнитель (любой авторизованный — в отличие от `is_paid` заказа — тот меняет только админ, 403 `PAID_ADMIN_ONLY`).
- D63. Данные (миграция 0011, `ALTER TABLE subtasks`): `is_executor_paid boolean NOT NULL DEFAULT false`, `executor_paid_at timestamptz NULL` (now() при переходе false→true, NULL при снятии, при повторном true не меняется — как `paid_at` заказа), `executor_payout numeric(12,2) NULL CHECK (>= 0)` — сумма выплаты исполнителю, отдельная от `price` (цена для клиента). Частичный индекс `subtasks_executor_unpaid_idx (assignee_id) WHERE assignee_id IS NOT NULL AND NOT is_executor_paid`. Связь «отметка ⇒ есть исполнитель» держит сервис, не CHECK: `assignee_id` — ON DELETE SET NULL, удаление сотрудника не должно упираться в выплаченные услуги (такая услуга выпадает из отчёта; отметку в карточке можно снять).
- D64. Сумма выплаты редактируется независимо от флага (можно задать до отметки и править после); итоги считают `COALESCE(executor_payout, 0)` — услуга без суммы даёт 0.
- D65. Карточка заказа — через существующий `PUT /api/v1/subtasks/:id`: новые поля `is_executor_paid` и `executor_payout` — НЕ часть полной замены строки, потому что у них есть второй писатель (отчёт «Выплаты», D70): поле, которого нет в теле, не меняется (`is_executor_paid`: нет поля → флаг прежний; `executor_payout`: нет поля → сумма прежняя, явный `null` → очистить, число → установить; тип запроса `OptionalAmount`). Карточка (`task-card.js`) шлёт эти поля только когда пользователь правит именно их — правка срока/статуса/цены из устаревшей карточки не снимает и не возвращает чужую отметку и не трогает сумму. `price` — по-прежнему полная замена (as-is). В ответе карточки у услуги — `is_executor_paid`, `executor_paid_at`, `executor_payout`. Перевести флаг false→true можно только при назначенном исполнителе → иначе 400 `is_executor_paid: no_assignee`. *(уточнено по code review 2026-10-05)*
- D66. Сменить или снять СУЩЕСТВУЮЩЕГО исполнителя у выплаченной услуги нельзя, пока отметка остаётся → 409 `SUBTASK_EXECUTOR_PAID`; сначала снять отметку (снятие отметки и смена исполнителя одним запросом допустимы — итоговое состояние согласовано). Правила — по переходу, не по итоговому состоянию: выплаченная услуга, оставшаяся без исполнителя (сотрудника удалили, `ON DELETE SET NULL`), правится свободно, и ей можно назначить исполнителя (NULL → uuid); 400 `no_assignee` — только когда запрос сам переводит флаг false→true без исполнителя. *(уточнено по code review 2026-10-05)*
- D67. Доска: фильтр «Выплата исполнителю» рядом с фильтром оплаты — `GET /api/v1/tasks?executor_paid=all|paid|unpaid` (иное → 400 по полю). `unpaid` — у заказа есть услуга с исполнителем и `is_executor_paid=false`; `paid` — услуги с исполнителем есть и все они выплачены; заказ без услуг с исполнителем не входит ни в `paid`, ни в `unpaid`.
- D68. Доска: метка «💸 к выплате: N» на карточке заказа — `executor_unpaid_done` в элементах `GET /tasks` и в `GET /tasks/:id`: число услуг `status=done` с исполнителем без отметки выплаты (0 — метки нет).
- D69. Экран-отчёт «Выплаты» (`/executor-payouts`, пункт «Работа → Выплаты», доступен и исполнителю): группировка исполнитель → его услуги (заказ #, услуга, статус, цена, сумма выплаты, выплачено/дата), итоги по исполнителю и общие «к выплате / выплачено», фильтры `assignee=me|all|<uuid>` (без параметра: исполнитель — «мои», админ — все; исполнитель может переключиться на «все» — аналог D19), `status=all|paid|unpaid`, `only_done=true|false`. API: `GET /api/v1/executor-payouts` — услуги с исполнителем, конверт `{items,total,limit,offset}` (limit по умолчанию 200, max 1000), порядок — исполнитель, заказ, позиция услуги; `GET /api/v1/executor-payouts/summary` — итоги по исполнителям под теми же фильтрами (`unpaid_count`, `paid_count`, `to_pay`, `paid`), отдельным эндпоинтом по образцу `/stock/summary`, тот же конверт. Код — отдельный пакет `internal/features/executorpayouts` (не board, по образцу D50); правка одной услуги остаётся в board.
- D70. Массовая отметка: `POST /api/v1/executor-payouts/mark {subtask_ids:[…], is_executor_paid}` — атомарно в одной транзакции (Lock Order как у board: заказы по id → услуги по id); ответ `{updated}` — сколько услуг реально сменило отметку (повтор идемпотентен, дата прежней отметки сохраняется). Ошибки — 400 по индексу: `subtask_ids[i]: invalid|duplicate|not_found|no_assignee`, пустой список — `required`, больше 500 — `too_many`, нет `is_executor_paid` — `required`; при любой ошибке ничего не меняется. Снять отметку можно и у услуги без исполнителя. Экран шлёт в запрос только выбранные услуги, чья отметка отличается от целевой; если таких больше 500 — сообщение «не более 500», запрос не уходит и на части не режется (атомарность).

- D72. Сумма выплаты правится прямо на экране «Выплаты» (решение пользователя 2026-10-05): в колонке «Выплата» — инлайн-поле (сохранение по Enter/уходу из поля, только если значение изменилось; пустое — «не задана»; на время запроса поле заблокировано; ошибка — сообщение и откат значения), после сохранения итоги перезапрашиваются (`/summary`), выбор чекбоксов и фильтры не сбрасываются. Поле — текстовое с `inputmode="decimal"`, разбор как в карточке заказа (запятая → точка; невалидный ввод — сообщение и откат, не очистка). После сохранения обновляются точечно только поле этой строки, шапки групп и общие итоги — остальные строки не пересоздаются, фокус и набранное в соседних полях сохраняются; массовая отметка и смена фильтра дожидаются незавершённых сохранений сумм. API: `PUT /api/v1/executor-payouts/:id` (id — uuid услуги), тело `{"executor_payout": число|null}` — поле обязательно (нет поля → 400 `executor_payout: required`; `null` — очистить; число — NUMERIC(12,2) ≥ 0, те же коды, что в карточке); меняет ТОЛЬКО сумму — флаг, дата отметки, цена, статус и исполнитель не трогаются (поэтому отчёт не ходит через `PUT /subtasks/:id` с его полной заменой). Права — admin и executor (D62). Ответ — строка отчёта в виде элемента `GET /executor-payouts`. Битый uuid в пути → 400 `id: invalid`; услуги нет ИЛИ у неё нет исполнителя → 404 `EXECUTOR_PAYOUT_NOT_FOUND`: ресурс — строка отчёта, а услуга без исполнителя в отчёт не входит (в ответе `assignee_id/assignee_name` не бывают null); сумму такой услуги по-прежнему правят в карточке заказа (D64/D65 — сумма независима от флага и исполнителя). Блокировки — как у mark (заказ → услуга).
